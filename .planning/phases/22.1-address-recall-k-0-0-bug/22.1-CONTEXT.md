# Phase 22.1: address-recall-k-0-0-bug — Context

**Gathered:** 2026-04-25
**Status:** Ready for planning

<domain>
## Phase Boundary

Fix two root-cause bugs that cause recall@k10 and recall@k50 to report 0.0 for Weaviate and Qdrant, then verify the fix with a local smoke test (`--upsert-limit 10 --query-limit 10 --db all`).

Bug 1: `ChromaDBLoader.query()` queries a phantom empty collection instead of the loaded data — collection name not resolved through `CHROMADB_COLLECTION_NAMES`.

Bug 2: `WeaviateLoader.query()` returns UUID strings instead of `doc_id` strings — no `doc_id_str` property stored in Weaviate objects; fallback `str(obj.uuid)` produces UUIDs that never match ChromaDB baseline IDs.

</domain>

<decisions>
## Implementation Decisions

### Weaviate Schema Reset
- **D-01:** Drop and recreate Weaviate collections as a **manual pre-smoke-test step**, not via code. The planner documents the exact shell command as a prerequisite step before running the smoke test.
  - Command: `docker compose -f infra/docker-compose.vector-dbs.yml down -v && docker compose -f infra/docker-compose.vector-dbs.yml up -d`
  - Rationale: benchmark Weaviate instance is ephemeral; wiping the volume is the clean, expected operation. No new reset_schema() method or auto-detect logic needed.

### Test Coverage
- **D-02:** **Smoke test only** — no new unit tests for these bug fixes.
  - The smoke test (`--upsert-limit 10 --query-limit 10 --db all`) is the acceptance proof per SPEC Req 4. Both bugs are in integration-layer code (live DB connections) where meaningful tests require mocking clients. Smoke test is the real proof of correctness.

### Claude's Discretion
- Whether to add `return_properties=["doc_id_str"]` to `WeaviateLoader.query()` for efficiency (minor optimization — omitting returns all props, which works fine)
- Docstring updates to reflect that `ChromaDBLoader.query()` now accepts collection aliases
- Exact wording of the pre-smoke-test checklist steps in PLAN.md

</decisions>

## Specific Ideas

- The exact fix for Bug 1 is one line before `get_or_create_collection`: `coll_name = CHROMADB_COLLECTION_NAMES.get(collection, collection)`

- After adding `doc_id_str`, existing Weaviate collections must be wiped before smoke test — `_ensure_schema()` only creates collections that don't exist yet

<code_context>
## Existing Code Insights

### Reusable Assets
- `CHROMADB_COLLECTION_NAMES` (config/pipeline_config.py): Already imported in `chromadb_loader.py` — the fix uses `.get(collection, collection)` on this dict
- `generate_uuid5` (weaviate.util): Already used in `load()` to derive deterministic UUIDs from doc_id strings — confirms doc_id is available at insert time
- `Property(name=..., data_type=DataType.TEXT)` pattern: Already used throughout `_*_properties()` methods — adding `doc_id_str` follows the same pattern

### Established Patterns
- `load()` passes `properties=meta` to `batch_ctx.add_object()` — the fix injects `doc_id_str` inline: `properties={**meta, "doc_id_str": doc_id}`
- `_ensure_schema()` uses `if not self._client.collections.exists(name)` guard — idempotent but does NOT update existing schemas; existing collections must be dropped for schema changes to apply
- Phase 22 established class-per-loader pattern with `load()` / `query()` / `close()` — this phase modifies methods within that pattern, not the structure

### Integration Points
- `benchmark/runner.py` calls `ChromaDBLoader.query()` in `_collect_chroma_baseline()` (lines 600–627); the Bug 1 fix makes these calls return real IDs instead of empty lists
- `benchmark/runner.py` calls `WeaviateLoader.query()` in `run_recall()`; Bug 2 fix makes returned IDs intersect correctly with the ChromaDB baseline

</code_context>
