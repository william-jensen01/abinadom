# Phase 22.1: address-recall-k-0-0-bug — Specification

**Created:** 2026-04-25
**Ambiguity score:** 0.165 (gate: ≤ 0.20)
**Requirements:** 4 locked

## Goal

Fix two root-cause bugs that cause recall@k10 and recall@k50 to report 0.0 for Weaviate and Qdrant, and verify the fix with a local smoke test (`--upsert-limit 10 --query-limit 10 --db all`).

## Background

Phase 22 shipped a benchmark runner that reports recall@k by comparing Weaviate and Qdrant result IDs against ChromaDB's as ground-truth. Existing benchmark results show `"recall": {"mean_k10": 0.0, "mean_k50": 0.0}` for both Weaviate and Qdrant.

Two independent bugs produce this zero:

**Bug 1 — ChromaDB collection name mismatch (`loaders/chromadb_loader.py:130`)**
`ChromaDBLoader.query()` calls `get_or_create_collection(name=collection)` with the raw collection argument (e.g. `"paragraphs"`). However, `load()` stores data into `CHROMADB_COLLECTION_NAMES["paragraphs"]` = `"conference_talk_paragraphs"`. The query hits a newly auto-created empty collection, not the loaded data. `_collect_chroma_baseline()` in `runner.py:600–627` also uses `ChromaDBLoader.query()`, so the baseline dict has empty ID lists for every query. The `if not baseline_ids: continue` guard in `run_recall()` then skips all queries, leaving `k10_scores = []` and returning 0.0.

**Bug 2 — Weaviate returns UUIDs instead of doc_ids (`loaders/weaviate_loader.py:299`)**
`WeaviateLoader.query()` returns `obj.properties.get("id", str(obj.uuid))`. The properties dict has no field named `"id"`, so it falls back to `str(obj.uuid)` — a UUID5 derived deterministically from the doc_id string via `generate_uuid5(doc_id)`. ChromaDB baseline IDs are `"para_1234"` style strings. UUID ≠ doc_id → zero set intersection → recall@k = 0.0 even if Bug 1 were fixed independently.

Qdrant is already correct: `query()` returns `hit.payload.get("_doc_id", str(hit.id))`, and `load()` stores `"_doc_id": doc_id` in the payload. No Qdrant changes are needed.

## Requirements

1. **ChromaDB query collection mapping**: `ChromaDBLoader.query()` must resolve the collection argument through `CHROMADB_COLLECTION_NAMES` before querying, matching the resolution used in `load()`.
   - Current: `col = self._client.get_or_create_collection(name=collection)` with `collection="paragraphs"` creates/queries an empty collection named `"paragraphs"`
   - Target: `coll_name = CHROMADB_COLLECTION_NAMES.get(collection, collection)` applied before `get_or_create_collection`, so `"paragraphs"` resolves to `"conference_talk_paragraphs"`
   - Acceptance: A `ChromaDBLoader.query(collection="paragraphs", ...)` call on a ChromaDB instance loaded via `ChromaDBLoader.load()` returns a non-empty list of IDs

2. **Weaviate doc_id property in schema**: All 4 Weaviate class schemas (Talk, Paragraph, Citation, Footnote) must include a TEXT property storing the original doc_id string. The property name must conform to Weaviate v4 naming rules (starts with lowercase letter) — use `doc_id_str`.
   - Current: No `doc_id_str` property exists in any Weaviate class schema; load() passes only the transformed metadata dict
   - Target: `_talk_properties()`, `_paragraph_properties()`, `_citation_properties()`, `_footnote_properties()` each include `Property(name="doc_id_str", data_type=DataType.TEXT)`; `load()` passes `{**meta, "doc_id_str": doc_id}` as properties for every record
   - Acceptance: After loading a talk bundle, querying a Weaviate object and reading `obj.properties["doc_id_str"]` returns the expected string (e.g. `"para_1234"`)

3. **Weaviate query returns doc_ids**: `WeaviateLoader.query()` must return the `doc_id_str` property value instead of the UUID fallback.
   - Current: `return [obj.properties.get("id", str(obj.uuid)) for obj in result.objects]` → returns UUID strings because `"id"` is not in properties
   - Target: `return [obj.properties.get("doc_id_str", str(obj.uuid)) for obj in result.objects]`
   - Acceptance: Running a query against a loaded Weaviate instance returns strings matching the `"para_N"` / `"cite_N_M"` / `"fn_N"` / `"talk_N"` format, not UUID-format strings

4. **Smoke test confirms non-zero recall**: A local benchmark run with `--upsert-limit 10 --query-limit 10 --db all` must produce JSON report files where both Weaviate and Qdrant show non-zero recall.
   - Current: `weaviate_*.json` and `qdrant_*.json` both contain `"recall": {"mean_k10": 0.0, "mean_k50": 0.0}`
   - Target: After code fixes, both reports contain `"recall": {"mean_k10": > 0.0, "mean_k50": > 0.0}`
   - Acceptance: Both report files exist and pass assertion `report["recall"]["mean_k10"] > 0.0 and report["recall"]["mean_k50"] > 0.0`

## Boundaries

**In scope:**
- `loaders/chromadb_loader.py` — fix `query()` collection name resolution (Req 1)
- `loaders/weaviate_loader.py` — add `doc_id_str` TEXT property to all 4 class schemas, update `load()` to store it, update `query()` to return it (Reqs 2, 3)
- Local smoke test run (`--upsert-limit 10 --query-limit 10 --db all`) and its JSON output (Req 4)
- Dropping and recreating Weaviate collections on the benchmark Docker instance to apply the schema change (acceptable — benchmark instance is ephemeral)

**Out of scope:**
- `loaders/qdrant_loader.py` — Qdrant already correctly returns `_doc_id` strings; no changes needed
- `benchmark/runner.py` — bugs are in the loaders and collection resolution, not in the runner orchestration logic; no changes needed
- `benchmark/queries.py` — canonical query collection names (`"paragraphs"`, `"citations"`) are correct for Weaviate and Qdrant; only ChromaDB needed a resolution layer
- Full 5,838-talk benchmark run — that is Phase 23's responsibility; this phase only needs a smoke test to confirm the fix works
- Changes to production ChromaDB loader (`extractors/phase6_chromadb_loader.py`) — that loader has a separate query path not used by the benchmark

## Constraints

- Weaviate property names must start with a lowercase letter per Weaviate v4 conventions. Use `doc_id_str` (not `_doc_id`).
- `_ensure_schema()` in `WeaviateLoader.__init__()` is idempotent (checks `.exists()` before creating). After adding `doc_id_str`, existing Weaviate collections created without this property must be cleared before the smoke test — dropping and recreating the benchmark Weaviate collections is the accepted resolution.
- The `CHROMADB_COLLECTION_NAMES` mapping import is already present in `chromadb_loader.py` (`from config.pipeline_config import CHROMADB_COLLECTION_NAMES`). No new imports needed.
- The smoke test must be run with all three DBs running via the benchmark Docker Compose stack (`infra/docker-compose.vector-dbs.yml`) and Ollama serving `nomic-embed-text`.

## Acceptance Criteria

- [ ] `ChromaDBLoader.query(collection="paragraphs", query_text=..., k=10)` on a loaded ChromaDB instance returns a non-empty list of IDs (not an empty list from a phantom collection)
- [ ] `WeaviateLoader.query(collection="paragraphs", query_text=..., k=10)` returns IDs in `"para_N"` format, not UUID-format strings
- [ ] All 4 Weaviate class schemas include `doc_id_str` as a TEXT property
- [ ] `WeaviateLoader.load()` stores `doc_id_str` in each object's properties
- [ ] Smoke test (`--upsert-limit 10 --query-limit 10 --db all`) completes without error
- [ ] `weaviate_*.json` smoke test report: `recall.mean_k10 > 0.0` AND `recall.mean_k50 > 0.0`
- [ ] `qdrant_*.json` smoke test report: `recall.mean_k10 > 0.0` AND `recall.mean_k50 > 0.0`
