## Critical Issues

### CR-01: Weaviate query() name_map fallback creates UnknownCollection error path

**File:** `loaders/weaviate_loader.py:284`

**Issue:** The query() method maps collection names to PascalCase class names, but if an unknown name is passed, `name_map.get(collection, collection)` returns the original string. When passed to `self._client.collections.use(class_name)` on line 285, this will raise an exception if the class doesn't exist. There is no error handling for this case, and the method signature allows arbitrary collection names (per the docstring: "Accept PascalCase directly too"), creating an unhandled exception path.

Example: `query(collection="unknown", ...)` will call `self._client.collections.use("unknown")` which fails without user-friendly error message.

**Fix:**
```python
class_name = name_map.get(collection, collection)
if class_name not in ["Talk", "Paragraph", "Citation", "Footnote"]:
    raise ValueError(f"Unknown collection: {collection!r}. Must be one of: talks, paragraphs, citations, footnotes, Talk, Paragraph, Citation, Footnote")
col = self._client.collections.use(class_name)
```

### CR-02: Benchmark run_recall() skips empty baselines, biasing mean_k10 and mean_k50 downward

**File:** `benchmark/runner.py:468-470`

**Issue:** The recall@k computation skips queries when `baseline_ids` is empty:
```python
baseline_ids = chroma_baseline.get(q["query_text"], [])
if not baseline_ids:
    continue  # ← SKIP THIS QUERY
```

This creates a silent bias: if any canonical query returns 0 results from ChromaDB, it is excluded from the recall mean. This violates the statistical property that all N queries should contribute to the mean. If 1 of 8 queries has empty baseline, the mean becomes mean(7 scores) instead of mean(8 scores), artificially inflating recall.

**Example:** If baseline["query_text_1"] = [] and all others have results, then k10_scores will have 7 entries (indices 0–6), and mean_k10 will be computed from only those 7, missing the 0.0 score for query_text_1.

**Fix:** Remove the skip condition and include empty baselines as recall=0.0:
```python
for q in self._queries:
    baseline_ids = chroma_baseline.get(q["query_text"], [])
    # if not baseline_ids:
    #     continue  ← DELETE THIS
    candidate_ids = self._query_db(q) or []
    # Query with empty baseline always produces recall=0.0, which is correct
    k10_scores.append(recall_at_k(baseline_ids, candidate_ids, k=10))
    # ... rest of loop
```

## Warnings

### WR-01: Weaviate query() imports Filter twice in same method

**File:** `loaders/weaviate_loader.py:291,296`

**Issue:** The Filter class is imported twice within the same query() method:
- Line 291: `from weaviate.classes.query import Filter` (inside the initial `if filter is not None`)
- Line 296: `from weaviate.classes.query import Filter` (inside the nested `else` block)

This is redundant and suggests copy-paste error. The second import is unreachable if there's only one condition, and both are within the same scope.

**Fix:** Move the import to the top of the method or module:
```python
def query(self, ...):
    from weaviate.classes.query import Filter
    
    # ... name mapping code ...
    
    if filter is not None:
        conditions = [Filter.by_property(prop).equal(v) for prop, v in filter.items()]
        if len(conditions) == 1:
            kwargs["filters"] = conditions[0]
        else:
            combined = conditions[0]
            for cond in conditions[1:]:
                combined = combined & cond
            kwargs["filters"] = combined
```

Or better yet, import at module level (line 23) since it's only used in one method.

### WR-02: Weaviate query() docstring claims return field is "id" but code uses "doc_id_str"

**File:** `loaders/weaviate_loader.py:270,303`

**Issue:** The docstring states:
```python
Returns:
    list[str] of document IDs (from the "id" metadata field).
```

But the actual implementation on line 303 is:
```python
return [obj.properties.get("doc_id_str", str(obj.uuid)) for obj in result.objects]
```

The code retrieves "doc_id_str" from properties, not "id". The docstring is inaccurate and will mislead callers about the data source. This contradicts Plan 02, which specifically added doc_id_str to fix the UUID fallback issue.

**Fix:** Update the docstring:
```python
Returns:
    list[str] of document IDs (from the "doc_id_str" metadata field, 
    falls back to UUID string if not present).
```

### WR-03: ChromaDB close() relies on undocumented private API (_server._session)

**File:** `loaders/chromadb_loader.py:100,105`

**Issue:** The close() method accesses private implementation details of the ChromaDB client:
```python
self._client._server._session.close()
if hasattr(self._client, "_admin_client"):
    self._client._admin_client._server._session.close()
```

This code assumes:
1. `_client._server` exists and has a `_session` attribute
2. `_client._admin_client` may exist and also has `_server._session`

These are private API implementation details (prefixed with `_`). If ChromaDB's internal structure changes in a minor version update, this code will break silently (caught by bare `except Exception`). The comment explains the reason (FastAPI has no stop() hook), but there's no fallback for newer ChromaDB versions that may have fixed this issue.

**Risk:** Silent failure to close connections on any ChromaDB version that changes internal structure. The bare `except Exception: pass` masks the failure.

**Recommendation:** Either:
1. Add a version check or capability detection before accessing private attributes
2. Remove these private-API calls and rely solely on `self._client.close()` (the public API)
3. Log a warning if the private API access fails instead of silently passing

Current version is acceptable as a workaround documented in comments, but fragile long-term.

### IN-02: Bare except: Exception in multiple places catches all errors equally

**File:** `benchmark/runner.py:181-184, 482, loaders/chromadb_loader.py:101-102,106-107`

**Issue:** Several bare `except Exception:` blocks catch all exceptions and continue or pass silently. While this is intentional for resilience (per D-07 error handling design), it masks some failures:

1. `runner.py:181-184` — `_timed_query()` logs and returns None on any exception, which is correct
2. `runner.py:482` — `run_recall()` catches exception on k=50 re-query and falls back to k=10 results — this changes what k50_scores measures without warning
3. `chromadb_loader.py:101-102,106-107` — bare except in close() suppresses any error closing private API sessions

The most concerning is `run_recall()` line 482: if re-querying with k=50 fails, it silently uses k=10 results as baseline for recall@k50 calculation, which measures recall@k10 instead. This is a silent measurement error.

**Recommendation:** Be more specific about exception types or add a debug log for the fallback case in run_recall():
```python
try:
    candidate_ids_50 = self._loader.query(...)
except Exception as e:
    logger.debug("[%s] re-query with k=50 failed: %s, using k=10 results instead", self._db_name, e)
    candidate_ids_50 = candidate_ids
```
