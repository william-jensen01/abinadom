# Phase 22.2: Optimize Benchmark Loaders for Efficiency — Specification

**Created:** 2026-04-26
**Ambiguity score:** 0.17 (gate: ≤ 0.20)
**Requirements:** 4 locked

## Goal

Reduce benchmark upsert time from 2–7 hours (5,838 talks at current rates) to a feasible range for Phase 23 by batching Ollama embedding calls within each talk bundle and parallelizing talk loading across all three DBs with a configurable thread pool.

## Background

Benchmark results from 2026-04-26 show upsert speed of 0.64 rps (ChromaDB), 0.23 rps (Weaviate), and 0.78 rps (Qdrant) for a 10-talk sample. Root cause: `loaders/shared_transforms.py` calls `embed_fn(text)` once per record (paragraph, citation, footnote) — a typical talk triggers 80–100 sequential HTTP calls to Ollama before a single DB write occurs.

Two fixes are locked:
1. **Batch embedding** — collect all texts from a talk bundle, call Ollama once with the full list, distribute vectors back. Ollama's `embed()` API accepts `input: list[str]`.
2. **Parallel talk loading** — `benchmark/runner.py` upsert phase uses a `ThreadPoolExecutor` with a configurable `--workers` flag. Weaviate's `load()` switches from the stateful `col.batch.fixed_size()` context manager to the stateless `col.data.insert_many()` API to support concurrent access.

## Requirements

1. **Batch embedding in embeddings.py**: A `embed_batch(texts: list[str]) -> list[list[float]]` function is added alongside the existing `embed()`.
   - Current: `embeddings.py` only exposes `embed(text: str)` — single Ollama call per text
   - Target: `embed_batch(texts)` sends all texts in one `_client.embed(model=model, input=texts)` call and returns a list of 768-dim vectors in the same order
   - Acceptance: calling `embed_batch(["a", "b", "c"])` returns a list of 3 vectors of length 768 in a single Ollama round-trip (verified by unit test with a mock Ollama client)

2. **Batch embedding in shared_transforms.py**: `prepare_talk_bundle()` and `prepare_talk_bundle_rich()` collect all document texts from the bundle, call `embed_fn` once with the full list, and distribute the resulting vectors back to each record.
   - Current: each `prepare_*` helper calls `embed_fn(document)` per record inside a loop — O(n) sequential calls per bundle
   - Target: all texts from a talk bundle (talks + paragraphs + citations + footnotes) are batched into one `embed_fn(texts: list[str])` call; `embed_fn` signature changes from `Callable[[str], list[float]]` to `Callable[[list[str]], list[list[float]]]`
   - Acceptance: loading a 10-talk sample with `--upsert-limit 10` triggers exactly 10 Ollama embed calls (one per talk bundle), not 800+ (verified by patching `embed_batch` with a call counter in tests)

3. **Weaviate loader uses `insert_many`**: `WeaviateLoader.load()` replaces the `col.batch.fixed_size()` context manager with `col.data.insert_many(objects)`.
   - Current: `load()` uses `with col.batch.fixed_size(batch_size=self.batch_size) as batch_ctx:` — stateful context manager, not safe for concurrent calls from multiple threads to the same collection
   - Target: `load()` builds a list of `weaviate.classes.data.DataObject` instances and calls `col.data.insert_many(objects)` for each collection; errors are logged from the returned result object
   - Acceptance: `WeaviateLoader.load()` completes without error on a sample bundle and the inserted records are retrievable via `query()` (existing `test_loaders_weaviate.py` passes, with test stubs updated as needed)

4. **Parallel talk loading in runner**: `benchmark/runner.py` upsert phase loads talks using a `ThreadPoolExecutor` with worker count controlled by `--workers N` (default 4).
   - Current: talks are loaded sequentially in a `for talk_id in talk_ids:` loop
   - Target: upsert phase submits each talk to a `ThreadPoolExecutor(max_workers=args.workers)` pool; each worker gets its own loader instance (separate DB connections); failures per talk are logged as WARNING without stopping other workers
   - Acceptance: `python benchmark/runner.py --db all --upsert-limit 10 --workers 4` completes without error; JSON report shows `records_per_second` higher than the pre-22.2 baseline (ChromaDB > 0.64, Weaviate > 0.23, Qdrant > 0.78) for all three DBs

## Boundaries

**In scope:**
- `loaders/embeddings.py` — add `embed_batch(texts: list[str])`
- `loaders/shared_transforms.py` — refactor `prepare_talk_bundle()` and `prepare_talk_bundle_rich()` to use batched embed; update `embed_fn` type from `Callable[[str], ...]` to `Callable[[list[str]], ...]`
- `loaders/weaviate_loader.py` — replace `col.batch.fixed_size()` with `col.data.insert_many()`
- `benchmark/runner.py` — add `--workers N` CLI flag (default 4); parallelize upsert phase with `ThreadPoolExecutor`
- `tests/test_loaders_*.py` — update stubs as needed for changed `embed_fn` signature

**Out of scope:**
- `extractors/phase6_chromadb_loader.py` — production loader is untouched; only benchmark loaders are modified
- Query performance — `query()` methods on all three loaders are unchanged
- Non-Ollama embedding providers — `embed_batch` targets `nomic-embed-text` only; no pluggable provider abstraction
- Recall@k fixes — addressed in Phase 22.1; not revisited here
- Schema management changes — `WeaviateLoader._ensure_schema()` stays as-is; pre-creation before parallel load is handled by loader `__init__` on first instantiation

## Constraints

- `embed_fn` type changes from `Callable[[str], list[float]]` to `Callable[[list[str]], list[list[float]]]` — callers (loaders, runner, any test stubs) must be updated consistently; the old single-text `embed()` remains in `embeddings.py` for backward compatibility with any non-benchmark callers
- Each thread in the runner pool instantiates its own loader (separate gRPC connection for Weaviate, separate HTTP session for ChromaDB/Qdrant) — no shared loader state across threads
- `--workers` default is 4; must be documented in `--help` output
- Vector dimension stays 768 (nomic-embed-text); no embedding model changes

## Acceptance Criteria

- [ ] `embed_batch(["a", "b"])` returns 2 vectors of length 768 in a single Ollama round-trip (unit test with mocked Ollama client)
- [ ] Loading a 10-talk sample triggers exactly 10 Ollama embed calls — one batched call per talk bundle (verified via call counter patch in tests)
- [ ] `WeaviateLoader.load()` uses `col.data.insert_many()` — no `col.batch.fixed_size()` context manager in the implementation
- [ ] `python benchmark/runner.py --help` shows `--workers` argument with default of 4
- [ ] `python benchmark/runner.py --db all --upsert-limit 10 --workers 4` completes without error and writes 3 JSON report files
- [ ] All three JSON reports show `upsert.records_per_second` above pre-22.2 baseline (ChromaDB > 0.64, Weaviate > 0.23, Qdrant > 0.78)
- [ ] `tests/test_loaders_chromadb.py`, `test_loaders_weaviate.py`, `test_loaders_qdrant.py` all pass (with allowable stub updates for `embed_fn` signature change)
