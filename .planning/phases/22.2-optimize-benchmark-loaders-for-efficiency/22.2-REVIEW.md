# Phase 22.2: Code Review Report

**Reviewed:** 2026-05-06T00:00:00Z
**Depth:** standard
**Files Reviewed:** 11
**Status:** issues_found

## Summary

Phase 22.2 introduced batched Ollama embedding (`embed_batch`), refactored `shared_transforms.py`
to a collect-embed-distribute pattern, updated type annotations, and parallelized the upsert phase
in `runner.py` with `ThreadPoolExecutor` and thread-local loaders.

The collect-embed-distribute pattern in the bundle-level functions (`prepare_talk_bundle`,
`prepare_talk_bundle_rich`) is structurally correct and does eliminate per-record embedding
round-trips. However, the refactor left a type contract violation in the individual `prepare_*`
helper functions, introduced a silent data-loss path when `embed_fn` returns a different number
of vectors than records, hardcoded the Weaviate gRPC port, and accepted a `url` parameter in
`embed_batch` that is silently ignored. Tests for ChromaDB and Qdrant loaders do not close
loader connections, leaking resources in integration test runs.

## Critical Issues

### CR-01: Individual `prepare_*` helpers call `embed_fn(document)` with a bare string — type contract violation and runtime crash

**File:** `loaders/shared_transforms.py:137, 188, 228, 264, 292, 317, 333, 349`

**Issue:** The `embed_fn` type annotation throughout `shared_transforms.py` is
`Callable[[list[str]], list[list[float]]]` — it accepts a list of strings and returns a list of
vectors. But every individual `prepare_*` function (not the bundle-level ones) calls
`embed_fn(document)` where `document` is a bare `str`. This is a type contract violation.

If any caller uses one of these individual functions directly with an `embed_fn` (the parameter
exists and is optional in all of them), the result depends on the underlying implementation:
- `embed_batch(texts)` calls `_client.embed(model=model, input=texts)`. Passing a bare string
  instead of a list causes Ollama to treat each character as a separate item (strings are
  iterable), or Ollama may emit an error. Either way the returned `list[list[float]]` will have
  length equal to `len(document)` not 1, making `embed_fn(document)` return a list of 768-dim
  vectors (one per character), and the caller assigns it directly to `vector` expecting a
  `list[float]` — a shape mismatch causing insertion of garbage data or a crash downstream.
- The bundle-level functions currently call these helpers with `embed_fn=None` and do the
  batch call separately, so the live path is not affected today. But the API surface is
  broken for any direct caller, and the silent mismatch is a maintenance trap.

**Fix:** Either remove the `embed_fn` parameter from the individual helpers entirely (since the
bundle-level functions handle embedding), or correct the call at each site:

```python
# Instead of:
vector = embed_fn(document) if embed_fn is not None else None

# Correct form (produces list[float] from a single-text batch):
vector = embed_fn([document])[0] if embed_fn is not None else None
```

### CR-02: `zip(all_records, vectors)` silently truncates records when `embed_fn` returns fewer vectors than expected

**File:** `loaders/shared_transforms.py:415-418, 488-492`

**Issue:** After the batch embed call, both `prepare_talk_bundle` and `prepare_talk_bundle_rich`
use `zip(all_records, vectors)` to merge records with embedding vectors. Python's `zip` truncates
to the shorter iterable without error. If `embed_fn` returns fewer vectors than there are records
(due to an Ollama partial failure, a count mismatch in a custom embed function, or any edge case),
the resulting `all_records` list is silently shorter than expected. The redistribute step then
slices with pre-computed lengths (`n_para = len(paragraph_records)`, etc.) derived from the
*original* counts — so the slice boundaries are wrong, producing collections with missing or
misattributed records. The data is silently corrupted without any log message.

**Fix:** Assert or check length equality after the embed call:

```python
vectors = embed_fn(texts)
if len(vectors) != len(all_records):
    logger.error(
        "embed_fn returned %d vectors for %d records — skipping bundle talk_id=%s",
        len(vectors), len(all_records), metadata.talk_id,
    )
    return {"talks": [], "paragraphs": [], "citations": [], "footnotes": []}
all_records = [
    (doc, meta, doc_id, vec)
    for (doc, meta, doc_id, _), vec in zip(all_records, vectors)
]
```

### CR-03: Weaviate gRPC port hardcoded at 50051 — not configurable via environment variable

**File:** `loaders/weaviate_loader.py:67`

**Issue:** The Weaviate client is constructed with a hardcoded `grpc_port=50051`:

```python
self._client = weaviate.connect_to_local(
    host=host,
    port=port,
    grpc_port=50051,
)
```

The HTTP port is injected via `host`/`port` arguments (and exposed in `_build_loader` via
`BENCHMARK_WEAVIATE_PORT`), but the gRPC port is always 50051. If the operator's Docker
deployment maps Weaviate's gRPC port to a different host port (e.g., 50052), the connection
will fail with a cryptic gRPC error. `runner.py` provides no `BENCHMARK_WEAVIATE_GRPC_PORT`
env var. This is especially relevant because the test defaults use port 8051 for HTTP (not the
standard 8080), suggesting the deployment is already non-standard.

**Fix:** Accept `grpc_port` as a constructor parameter (defaulting to 50051) and thread it
through `_build_loader`:

```python
# In WeaviateLoader.__init__:
def __init__(self, host, port, embed_fn, batch_size=100, grpc_port=50051):
    super().__init__(host, port, embed_fn, batch_size)
    self._client = weaviate.connect_to_local(host=host, port=port, grpc_port=grpc_port)
    self._ensure_schema()

# In runner.py _build_loader:
return WeaviateLoader(
    host=os.environ.get("BENCHMARK_WEAVIATE_HOST", "localhost"),
    port=int(os.environ.get("BENCHMARK_WEAVIATE_PORT", "8080")),
    grpc_port=int(os.environ.get("BENCHMARK_WEAVIATE_GRPC_PORT", "50051")),
    embed_fn=embed_batch,
    batch_size=100,
)
```

### CR-04: `embed_batch` / `embed` `url` parameter is silently ignored — callers cannot override the Ollama endpoint

**File:** `loaders/embeddings.py:35-54, 57-78`

**Issue:** Both `embed()` and `embed_batch()` accept a `url` parameter (documented in their
docstrings as "Ollama server URL") but never use it. The module-level singleton `_client` is
created at import time from the hardcoded `OLLAMA_URL = "http://localhost:11434"` and reused
for all calls, regardless of what `url` is passed:

```python
_client = ollama.Client(host=OLLAMA_URL)  # created once at import time

def embed_batch(texts, model="nomic-embed-text", url=OLLAMA_URL):
    response = _client.embed(model=model, input=texts)  # url is never used
    return [list(v) for v in response.embeddings]
```

Any caller that passes a custom `url` will silently receive embeddings from the default endpoint
rather than from the intended server. The `runner.py` pre-flight check at line 727 also calls
`embed("hello", model="nomic-embed-text")` without a custom URL, so there is no observable
failure — but the API surface is deceptive.

**Fix:** Either remove the `url` parameter from both functions (and document that the module-level
singleton is used), or restructure to accept a `url` and construct a per-call client:

```python
# Option A (simplest — remove the misleading parameter):
def embed_batch(texts: list[str], model: str = "nomic-embed-text") -> list[list[float]]:
    response = _client.embed(model=model, input=texts)
    return [list(v) for v in response.embeddings]

# Option B (honour the url parameter):
def embed_batch(texts, model="nomic-embed-text", url=OLLAMA_URL):
    client = ollama.Client(host=url)
    response = client.embed(model=model, input=texts)
    return [list(v) for v in response.embeddings]
```

## Warnings

### WR-01: `test_loaders_chromadb.py` and `test_loaders_qdrant.py` do not close loader connections

**File:** `tests/test_loaders_chromadb.py:26-47`, `tests/test_loaders_qdrant.py:27-40`

**Issue:** `TestChromaDBLoader.test_round_trip_paragraph` creates a `ChromaDBLoader` but never
calls `loader.close()`. `TestQdrantLoader.test_round_trip_paragraph` does the same for
`QdrantLoader`. The Weaviate test (`test_loaders_weaviate.py`) correctly uses `setup_method` /
`teardown_method` with `self.loader.close()`. The ChromaDB and Qdrant tests leave HTTP/gRPC
connections open for the process lifetime. When multiple tests run in a session, this
accumulates open file descriptors and may cause `ResourceWarning` noise. More importantly, it
is inconsistent with the explicit cleanup policy used in `WeaviateLoader` and documented in the
loaders' docstrings.

**Fix:** Add `setup_method` / `teardown_method` (matching the Weaviate test pattern), or use a
pytest fixture with `yield`:

```python
class TestChromaDBLoader:
    def setup_method(self, method):
        self.loader = None

    def teardown_method(self, method):
        if self.loader is not None:
            self.loader.close()

    def test_round_trip_paragraph(self, chromadb_available, talk_bundle):
        ...
        self.loader = ChromaDBLoader(...)
        self.loader.load(talk_bundle)
        ...
```

### WR-02: `_init_worker` registered with `atexit` — thread-local loader cleanup is deferred to process exit, not pool shutdown

**File:** `benchmark/runner.py:113-117`

**Issue:** Worker-thread loaders are cleaned up via `atexit.register(_tls.loader.close)`. This
means that for a `--db all` run (3 sequential `ThreadPoolExecutor` pools), each pool creates
N worker threads, each of which registers its loader with `atexit`. At process exit, all N×3
loaders are closed in LIFO order. If any intermediate pool's workers hold DB connections longer
than necessary (until exit rather than until the pool's `__exit__`), those connections occupy
resources during the Weaviate and Qdrant benchmark phases while ChromaDB connections are still
open. If the OS has a low file-descriptor limit, this could cause connection errors during the
later benchmarks.

A more robust pattern is to close loaders immediately when the `ThreadPoolExecutor` context
manager exits, by tracking them explicitly:

**Fix:**
```python
_tls = threading.local()
_worker_loaders_lock = threading.Lock()
_worker_loaders: list = []

def _init_worker(db_name: str, config: argparse.Namespace) -> None:
    _tls.loader = _build_loader(db_name, config)
    with _worker_loaders_lock:
        _worker_loaders.append(_tls.loader)

# After the `with ThreadPoolExecutor(...) as executor:` block:
with _worker_loaders_lock:
    for ldr in _worker_loaders:
        ldr.close()
    _worker_loaders.clear()
```

### WR-03: `run_serial_latency` includes failed-query latency in statistics, inflating error-path timing

**File:** `benchmark/runner.py:325-330`

**Issue:** `run_serial_latency` appends the round-trip time of a failed query to `latencies` and
separately increments `failed`. This means that failed queries (which return early with an
exception) contribute their (typically shorter) latency to the p50/p95/p99 computation, mixing
error-path timing with success-path timing. The same pattern appears in `run_filtered_unfiltered`
(lines 349-354). `_timed_query` (used in `run_scalability_curve` and `run_memory_query`)
correctly returns `None` on failure and the callers skip `None` values.

**Fix:** Match the `_timed_query` pattern — do not append to `latencies` on failure:

```python
for q in queries:
    t0 = time.monotonic()
    ids = self._query_db(q)
    elapsed = (time.monotonic() - t0) * 1000.0
    if ids is None:
        failed += 1
    else:
        latencies.append(elapsed)
```

### WR-04: `_atexit.register` called inside thread worker imports `atexit` on every thread initialization

**File:** `benchmark/runner.py:115`

**Issue:** `_init_worker` does `import atexit` inside the function body, which is called once
per worker thread. While Python caches module imports, the repeated `import atexit` inside a
tight-loop initializer is an unnecessary pattern — `atexit` is a stdlib module and should be
imported at module level alongside the other stdlib imports. This is a style issue but also
points to copy-paste construction since the rest of the file's imports are at the top.

**Fix:** Move the import to the top of the file (line 14-27 block already present):

```python
# In the module-level imports block (runner.py line 14-27):
import atexit
```

Then remove the `import atexit` line from inside `_init_worker`.

### WR-05: `test_loaders_qdrant.py` has no pre-test cleanup — stale records from prior runs can satisfy assertions non-deterministically

**File:** `tests/test_loaders_qdrant.py:27-40`

**Issue:** The Qdrant round-trip test queries with `limit=1` and asserts `talk_id == 9999` on the
top result. But the test never deletes any pre-existing points for `talk_id=9999` before loading.
If the collection already contains points from a prior test run, the `query_points` call can
return a stale point that happens to match `talk_id=9999`, making the test pass even if the
current `loader.load()` call silently failed. The ChromaDB test (line 31-32 in
`test_loaders_chromadb.py`) correctly pre-cleans with `col.delete(where={"talk_id": 9999})` —
the Qdrant test is missing the equivalent.

**Fix:**
```python
loader = QdrantLoader(...)
# Delete any stale points for talk_id=9999 before loading
from qdrant_client.models import Filter as QFilter, FieldCondition, MatchValue
loader._client.delete(
    collection_name="paragraphs",
    points_selector=QFilter(must=[FieldCondition(key="talk_id", match=MatchValue(value=9999))]),
)
loader.load(talk_bundle)
```

### IN-02: `loaders/embeddings.py` module-level `_client._client.close` accesses a private attribute — brittle against ollama library updates

**File:** `loaders/embeddings.py:28`

**Issue:** `atexit.register(_client._client.close)` accesses `_client` (private attribute of the
`ollama.Client` object) to close the underlying httpx session. This pattern was documented as
intentional but relies on the ollama library's internal implementation detail. A library version
bump that renames or restructures the internal client would silently stop the cleanup from
running, causing `ResourceWarning` on exit. The `try/except` used in `ChromaDBLoader.close()`
for the same pattern guards against this, but the `atexit` registration here does not.

**Fix:** Wrap in a guarded closure:
```python
def _close_ollama_client():
    try:
        _client._client.close()
    except Exception:
        pass

atexit.register(_close_ollama_client)
```
