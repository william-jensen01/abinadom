## Summary

After plan 04, JWT validation is working (OAUTH-02 covered), but the OAuth discovery chain
for Claude Desktop is incomplete. OAUTH-03 requires `/.well-known/oauth-protected-resource`
(RFC 9728) — the endpoint that tells MCP clients which authorization server (Auth0) to use.
mcpauth 0.1.1 does NOT serve this endpoint. It serves `/.well-known/oauth-authorization-server`
(RFC 8414, the AS metadata endpoint), which is also needed but is a separate spec.

The critical_context concern about algorithm-agnosticism is not actionable for Auth0 specifically:
Auth0 API access tokens default to RS256, the algorithm is configured at the API level (not the
client level), and HS256 tokens cannot be JWKS-verified by design. mcpauth's existing JWKS
verifier (`["RS256", "PS256", "ES256", "ES384", "ES512"]`) is correct for this setup.

**Primary recommendation:** Keep mcpauth for JWT verification (it works). Add a hand-written
RFC 9728 endpoint (`~20 lines`) serving `{"resource": MCP_BASE_URL, "authorization_servers":
["https://AUTH0_DOMAIN"]}`. Add the path-scoped variant `/.well-known/oauth-protected-resource/mcp`
as a second route. Verify mcpauth's 401 response includes `WWW-Authenticate: Bearer
resource_metadata=...`; add it if missing. This is the minimal change to close OAUTH-03 and
unblock OAUTH-01.

## Section 2: RFC 9728 — The Missing Endpoint

### What the MCP Spec Requires (Exact Discovery Order)

The MCP spec (2025-06-18 version) defines this discovery flow:

```
1. Client → MCP server: request without token
2. MCP server → Client: 401 + WWW-Authenticate: Bearer resource_metadata="<URL>"
3. Client → MCP server: GET <resource_metadata URL>
   OR fallback: GET /.well-known/oauth-protected-resource/{path-suffix}
   OR fallback: GET /.well-known/oauth-protected-resource
4. MCP server → Client: RFC 9728 JSON document
5. Client reads authorization_servers[0], constructs AS discovery URL
6. Client → Auth0: GET /.well-known/oauth-authorization-server (or openid-configuration)
7. Auth0 → Client: RFC 8414 AS metadata (endpoints, JWKS URI, etc.)
8. Client → browser: Auth0 authorize URL with PKCE + resource parameter
9. (user authenticates, gets code, exchanges for token)
10. Client → MCP server: request with Authorization: Bearer <JWT>
11. mcpauth validates JWT via PyJWKClient → Auth0 JWKS
```

[VERIFIED: modelcontextprotocol.io/specification/draft/basic/authorization, 2026-04-08]

Steps 2-4 are what is currently missing. Steps 6-11 are already covered by the existing code.

### RFC 9728 JSON Document Structure

```json
{
  "resource": "https://mcp.yourdomain.com",
  "authorization_servers": ["https://YOUR_TENANT.auth0.com"],
  "bearer_methods_supported": ["header"]
}
```

Fields:
- `resource` — canonical URI of this MCP server (the `MCP_BASE_URL` env var value)
- `authorization_servers` — array of trusted AS issuer URIs; Auth0 issuer is `https://{AUTH0_DOMAIN}` (no trailing slash at the domain level for this field; Auth0 JWT `iss` claim uses trailing slash)
- `bearer_methods_supported` — recommended; `["header"]` means Authorization header only

[CITED: https://datatracker.ietf.org/doc/html/rfc9728, verified against MCP spec examples]

### Why `/.well-known/oauth-authorization-server` Is Different

| Endpoint | Spec | Role | Served By |
|----------|------|------|-----------|
| `/.well-known/oauth-protected-resource` | RFC 9728 | Resource server self-description: "I am protected; use THIS Auth0 domain" | Must be added manually |
| `/.well-known/oauth-authorization-server` | RFC 8414 | Authorization server capabilities: "My authorize endpoint is X, token endpoint is Y" | Already served by `mcp_auth.metadata_route()` — proxies Auth0 OIDC config |

Claude Desktop reads RFC 9728 first (step 3), extracts the Auth0 domain from `authorization_servers`,
then constructs the RFC 8414 URL at Auth0 directly (step 6). The proxy in step 6 is only needed
if the client tries Auth0's RFC 8414 metadata via the MCP server's domain.

### wwW-Authenticate Header on 401

Confirmed by inspecting mcpauth source: `create_bearer_auth` returns 401 with:
```
WWW-Authenticate: Bearer error="..."
```

It does NOT include `resource_metadata=`. The resource_metadata parameter must be injected
to support the primary discovery path (step 2 above).

[VERIFIED: mcpauth source `create_bearer_auth` inspected — `WWW-Authenticate: Bearer` without `resource_metadata`]
[ASSUMED: this applies to all 401 responses from `bearer_auth_middleware`; verify during implementation]

## Section 3: Claude Desktop OAuth Flow End-to-End

Based on the MCP spec, Claude Desktop's expected flow:

```
Claude Desktop "Add MCP Server" dialog:
  1. Enter server URL (e.g., https://mcp.yourdomain.com)
  2. Claude Desktop → MCP server: POST /mcp (no token) — any MCP request
  3. MCP server → Claude Desktop: 401 + WWW-Authenticate: Bearer resource_metadata="https://mcp.yourdomain.com/.well-known/oauth-protected-resource"
  4. Claude Desktop → MCP server: GET /.well-known/oauth-protected-resource
  5. MCP server returns: {"resource": "...", "authorization_servers": ["https://xxx.auth0.com"]}
  6. Claude Desktop → Auth0: GET https://xxx.auth0.com/.well-known/oauth-authorization-server
  7. Auth0 returns: AS metadata (authorize_endpoint, token_endpoint, registration_endpoint, etc.)
  8. Claude Desktop registers as DCR client: POST https://xxx.auth0.com/oidc/register
  9. Auth0 returns: client_id, client_secret (or uses client_id_metadata_document approach)
  10. Claude Desktop → browser: https://xxx.auth0.com/authorize?...&code_challenge=...&resource=MCP_BASE_URL
  11. User authenticates via Auth0 Universal Login (Google/GitHub/email)
  12. Auth0 redirects to: https://claude.ai/api/mcp/auth_callback?code=...
  13. Claude Desktop exchanges code: POST https://xxx.auth0.com/oauth/token with code_verifier + resource
  14. Auth0 issues: RS256 JWT with aud=MCP_BASE_URL, iss=https://xxx.auth0.com/
  15. Claude Desktop → MCP server: request + Authorization: Bearer <JWT>
  16. mcpauth validates JWT via JWKS → request proceeds
```

**Key operator prerequisites (not code):**
- Auth0 API registered with identifier = `MCP_BASE_URL`
- Auth0 API signing algorithm = RS256 (default)
- DCR enabled on Auth0 tenant (Settings → Advanced → Enable OIDC Dynamic Client Registration)
- Callback URL `https://claude.ai/api/mcp/auth_callback` in Auth0 Allowed Callback URLs
- Google and GitHub social connections enabled

## Section 4: JWT Verification (mcpauth internals — confirmed working)

### How mcpauth Verifies JWTs

Calling chain when a request hits `bearer_auth_middleware("jwt", audience=MCP_BASE_URL)`:

```
bearer_auth_middleware("jwt", audience=MCP_BASE_URL)
  → create_verify_jwt(auth_server_config.metadata.jwks_uri)
    → PyJWKClient(jwks_uri,
                  headers={"user-agent": "@mcp-auth/python"})
    → per request:
        signing_key = PyJWKClient.get_signing_key_from_jwt(token)
            # reads kid from unverified header
            # matches against cached JWKS
            # if kid not found: refreshes JWKS once, retries
        jwt.decode(token, signing_key.key,
                   algorithms=["RS256", "PS256", "ES256", "ES384", "ES512"],
                   options={"verify_aud": False, "verify_iss": False})
        # audience validated separately via BearerAuthConfig.audience=MCP_BASE_URL
```

[VERIFIED: mcpauth source `create_verify_jwt`, `get_signing_key`, `PyJWKClient.__init__`]

### Algorithm Whitelist Assessment

mcpauth uses: `["RS256", "PS256", "ES256", "ES384", "ES512"]`

- **RS256** — Auth0 API default. This is what will be used. Covered.
- **ES256/ES384/ES512** — ECDSA variants. Covered.
- **PS256** — RSA-PSS variant. Covered.
- **HS256/HS384/HS512** — Excluded. Correct: symmetric keys are not published in JWKS.
  Auth0 HS256 API tokens cannot be verified via JWKS by design.

**DCR client concern from critical_context:** Auth0 API tokens are signed at the **API level**,
not the client level. A DCR-registered client accessing an Auth0 API configured for RS256 receives
RS256 tokens regardless of any client-level algorithm setting. The concern is not applicable for
Auth0 as the AS. No algorithm-agnosticism code is needed.

[CITED: auth0 community — API signing algorithm is API-level configuration, independent of client registration]
[VERIFIED: mcpauth `create_verify_jwt` source — algorithm list confirmed RS256 included, HS256 excluded]

### JWKS Caching (key rotation handled)

- **Tier 1 (JWK Set cache):** Default 300-second TTL (5 minutes)
- **Key rotation:** On unknown `kid`, mcpauth refreshes JWKS once and retries before failing
- **No manual cache management needed**

[VERIFIED: `PyJWKClient.__init__` source, `get_signing_key` source]

### RFC 9728 Endpoint Implementation

```python
# Source: RFC 9728 + MCP spec [VERIFIED: modelcontextprotocol.io/specification/draft/basic/authorization]
# Add to server.py alongside _auth_server_metadata()

async def _protected_resource_metadata(request: Request) -> JSONResponse:
    """Serve OAuth 2.0 Protected Resource Metadata (RFC 9728).

    Tells MCP clients which authorization server handles tokens for this resource.
    Required by MCP spec for OAuth discovery.
    Paths: /.well-known/oauth-protected-resource
           /.well-known/oauth-protected-resource/mcp
    """
    if not AUTH0_DOMAIN or not MCP_BASE_URL:
        return JSONResponse({"error": "OAuth not configured"}, status_code=404)

    doc = {
        "resource": MCP_BASE_URL,
        "authorization_servers": [f"https://{AUTH0_DOMAIN}"],
        "bearer_methods_supported": ["header"],
    }
    response = JSONResponse(doc)
    # CORS headers: MCP clients (browser-based) may fetch this cross-origin
    response.headers["Access-Control-Allow-Origin"] = "*"
    response.headers["Access-Control-Allow-Methods"] = "GET, OPTIONS"
    return response
```

### Route Registration in `build_app()` (OAuth mode)

```python
# Source: current server.py build_app() + RFC 9728 additions
routes = [
    Route("/health", endpoint=health_check),                                    # public
    Route("/.well-known/oauth-protected-resource",                              # RFC 9728 root
          endpoint=_protected_resource_metadata),
    Route("/.well-known/oauth-protected-resource/mcp",                         # RFC 9728 path-scoped
          endpoint=_protected_resource_metadata),
    mcp_auth.metadata_route(),        # /.well-known/oauth-authorization-server (mcpauth, RFC 8414)
    Route("/.well-known/oauth-authorization-server-proxy",

]
```

The `/.well-known/` routes must appear BEFORE `Mount("/")` or they will be unreachable.

## Section 8: Common Pitfalls

### Pitfall 1: Confusing RFC 9728 and RFC 8414 Endpoints
**What goes wrong:** Adding the RFC 8414 path (`/.well-known/oauth-authorization-server`) when
RFC 9728 (`/.well-known/oauth-protected-resource`) is what's needed.
**Why it happens:** Both are "well-known OAuth endpoints"; easy to conflate.
**How to avoid:** RFC 9728 is served by the RESOURCE SERVER describing itself. RFC 8414 is
served by the AUTHORIZATION SERVER describing its capabilities. We serve the former; Auth0 serves
the latter. mcpauth's `metadata_route()` proxies Auth0's RFC 8414 doc — it is NOT RFC 9728.

### Pitfall 2: Starlette Route Ordering with Mount("/")
**What goes wrong:** `/.well-known/` routes return 404 or fall into the MCP mount.
**Why it happens:** Starlette is first-match; `Mount("/")` catches everything.
**How to avoid:** All well-known routes must be listed BEFORE `Mount("/", app=mcp_app, ...)`.
**Warning signs:** Well-known endpoints return 404 or MCP-style error responses.

### Pitfall 3: Auth0 authorization_servers Field Value
**What goes wrong:** `authorization_servers` contains `https://tenant.auth0.com/` (with trailing
slash) but Auth0's RFC 8414 metadata has `issuer: "https://tenant.auth0.com/"` — clients
construct the well-known URL as `https://tenant.auth0.com/.well-known/oauth-authorization-server`
which is valid. However, if `authorization_servers` is `https://tenant.auth0.com` (no slash),
clients construct the same URL. Both work for URL construction.
**Auth0 JWT `iss` claim IS trailing-slash** — this matters for PyJWT's issuer check, but mcpauth
disables `verify_iss` in `decode()` options, so it does not affect runtime.
**How to avoid:** Serve `"https://{AUTH0_DOMAIN}"` (no trailing slash) in `authorization_servers`
— this is the Auth0 issuer identifier format consistent with RFC 8414.

### Pitfall 4: Missing Auth0 API Registration
**What goes wrong:** Auth0 issues tokens with `aud=None` or wrong audience; mcpauth rejects them.
**Why it happens:** Auth0 only includes the `aud` claim in access tokens when a specific API
(Resource Server) is registered and the `audience` parameter is included in the token request.
**How to avoid:** Operator must register an API in Auth0 with identifier = `MCP_BASE_URL` before
testing end-to-end. Without this, tokens will not have the correct audience.
**Warning signs:** `audience_mismatch` or `invalid_token` errors in mcpauth logs.

### Pitfall 5: Auth0 DCR Not Enabled for Claude Desktop
**What goes wrong:** Claude Desktop's DCR registration request returns 404 or 403 from Auth0.
**Why it happens:** Auth0 does not enable OIDC Dynamic Client Registration by default.
**How to avoid:** Enable in Auth0 dashboard: Settings → Advanced → OIDC Dynamic Client Registration.
**Note:** If Claude Desktop uses Client ID Metadata Documents instead of DCR, this step may not
be required. The MCP spec prefers Client ID Metadata Documents over DCR.

### Pitfall 6: Auth0 Issuer Trailing Slash (PyJWT direct use)
**What goes wrong:** If `jwt.decode()` is called directly (not via mcpauth), issuer check fails.
**Why it happens:** Auth0 JWT `iss` = `https://tenant.auth0.com/` (trailing slash). PyJWT's
issuer check is exact-match — passing `https://tenant.auth0.com` (no slash) fails.
**How to avoid:** When calling `jwt.decode()` directly, always use `f"https://{AUTH0_DOMAIN}/"`.
**Not applicable for the mcpauth path** — mcpauth disables `verify_iss` in decode options.

|---------------|---------|-----------------|

### Threat Register (additions to Plan 04 model)

| Threat | Category | Mitigation |
|--------|----------|-----------|
| RFC 9728 endpoint returns wrong AS | Spoofing | `authorization_servers` built from `AUTH0_DOMAIN` env var (operator-set, not user input) |
| Client fetches forged resource metadata | Spoofing | Endpoint served from MCP server's own domain; HTTPS guaranteed by Caddy/Cloudflare (Phase 16) |
| Token issued for wrong audience accepted | Elevation of Privilege | `bearer_auth_middleware(audience=MCP_BASE_URL)` rejects tokens with wrong audience |
| 401 response missing resource_metadata hint | Information Disclosure | If missing, clients cannot auto-discover; implementation must include it |
