# Phase 16.1: OAuth 2.0 for Claude Desktop - Research

**Researched:** 2026-04-06
**Domain:** OAuth 2.1 / MCP Auth / Python MCP SDK / Auth0
**Confidence:** HIGH (core integration pattern verified against installed package source)

## Summary

This phase adds OAuth 2.1 token validation to the MCP server so that Claude Desktop (and claude.ai connectors) can authenticate via a browser OAuth flow rather than manual bearer token copy-paste. The server is a pure Resource Server: Auth0 issues tokens, the MCP server validates them.

The installed `mcp` 1.26.0 package already ships everything needed: `TokenVerifier` protocol, `AuthSettings`, `create_protected_resource_routes`, `BearerAuthBackend`, `RequireAuthMiddleware`, and `AuthenticationMiddleware`. The integration point is the `FastMCP.__init__` constructor — pass `auth=AuthSettings(...)` plus a `token_verifier=` implementation built on PyJWT's `PyJWKClient`. The existing `BearerAuthMiddleware` (Phase 14 static token validation) must remain functional alongside the new OAuth path; the two are layered with different fallback logic.

**Critical caveat discovered:** Claude Desktop's built-in "Add custom connector" OAuth flow has a documented bug (as of late 2025) where the browser opens `about:blank` rather than the Auth0 login page for some server configurations. Claude Code CLI and MCP Inspector work reliably. The ROADMAP success criterion says "Claude Desktop OAuth handshake completes" — the implementation must be fully spec-compliant (RFC 8414 + RFC 9728), but end-to-end verification may require Claude Code CLI as the primary test client, with Claude Desktop tested as a best-effort target. A separate Cloudflare bot-blocking issue affecting claude.ai connectors must also be mitigated.

**Primary recommendation:** Use `mcp` SDK 1.26.0's built-in `TokenVerifier` protocol with a custom `Auth0JWTVerifier` class backed by PyJWT's `PyJWKClient`. Wire it into FastMCP via `auth=AuthSettings(issuer_url=..., resource_server_url=...)` + `token_verifier=Auth0JWTVerifier(...)`. Preserve existing `BearerAuthMiddleware` as a Starlette middleware layer on the returned `streamable_http_app()` — but restructure startup so both coexist correctly.

## Research Correction: mcpauth vs. mcp SDK

**D-06 and D-07 in CONTEXT.md reference the `mcpauth` pip package.** Research reveals a more important fact: the installed `mcp` 1.26.0 SDK already provides all the primitives that `mcpauth` would supply, directly in `mcp.server.auth`. The `mcpauth` package (v0.2.0b1, beta, JavaScript-primary docs) does not need to be installed separately.

This is Claude's discretion territory (exact integration pattern). The recommendation is to use the `mcp` SDK's built-in classes rather than add a beta dependency, because:
1. `mcp` 1.26.0 ships `TokenVerifier` protocol, `AuthSettings`, `create_protected_resource_routes`, `BearerAuthBackend`, `RequireAuthMiddleware` — all verified in installed source
2. `mcpauth` Python package is v0.2.0b1 (beta), JavaScript-primary documentation, Python examples sparse
3. Both the FastMCP `auth=` parameter and `mcp.server.auth.routes` are already wired into `mcp.streamable_http_app()`

## Architecture Patterns

### How the mcp 1.26.0 Auth System Works (verified from source)

`FastMCP.__init__` accepts:
```python
FastMCP(
    name="...",
    auth=AuthSettings(issuer_url=..., resource_server_url=...),
    token_verifier=<TokenVerifier>,   # custom implementation
    # OR
    auth_server_provider=<OAuthAuthorizationServerProvider>,  # full AS mode
)
```

When `auth` + `token_verifier` are provided, `streamable_http_app()` automatically:
1. Adds `AuthenticationMiddleware(backend=BearerAuthBackend(token_verifier))` to Starlette middleware
2. Wraps the MCP endpoint in `RequireAuthMiddleware(required_scopes, resource_metadata_url)`
3. Registers `/.well-known/oauth-protected-resource/mcp` route (RFC 9728) via `create_protected_resource_routes`
4. Sets `WWW-Authenticate: Bearer resource_metadata="..."` in 401 responses

**CONFLICT with current server.py**: The current code calls `mcp.streamable_http_app()` and then calls `app.add_middleware(BearerAuthMiddleware, store=store)` — Phase 14's custom middleware is bolted on after the fact. When `auth=` is passed to `FastMCP`, the SDK's own auth middleware is wired inside `streamable_http_app()`. Both must coexist.

### Recommended Project Structure
```
auth/
├── middleware.py      — BearerAuthMiddleware (Phase 14 static tokens — keep)
├── store.py           — SqliteKeyStore (keep unchanged)
└── oauth.py           — NEW: Auth0JWTVerifier(TokenVerifier) + dual-path logic
server.py              — Wire auth= + token_verifier= into FastMCP constructor

```

### Pattern 1: Auth0JWTVerifier (Custom TokenVerifier)

The `TokenVerifier` protocol requires one async method:
```python
async def verify_token(self, token: str) -> AccessToken | None: ...
```

Implementation using PyJWT:
```python
# auth/oauth.py
import os
import jwt
from jwt import PyJWKClient
from mcp.server.auth.provider import AccessToken, TokenVerifier

class Auth0JWTVerifier:
    """Validate Auth0-issued JWTs against Auth0's JWKS endpoint."""

    def __init__(self, domain: str, audience: str) -> None:
        self._audience = audience
        self._issuer = f"https://{domain}/"
        self._jwks_client = PyJWKClient(
            f"https://{domain}/.well-known/jwks.json",
            cache_keys=True,
            cache_jwk_set=True,
            lifespan=300,  # 5-minute JWKS cache
        )

    async def verify_token(self, token: str) -> AccessToken | None:
        try:
            signing_key = self._jwks_client.get_signing_key_from_jwt(token)
            payload = jwt.decode(
                token,
                signing_key.key,
                algorithms=["RS256"],
                audience=self._audience,
                issuer=self._issuer,
            )
            return AccessToken(
                token=token,
                client_id=payload.get("sub", "unknown"),
                scopes=payload.get("scope", "").split(),
            )
        except Exception:
            return None
```

### Pattern 2: FastMCP Auth Wiring

```python

from auth.oauth import Auth0JWTVerifier
```

### Pattern 3: Dual-Path Auth (Bearer Token Coexistence — D-08)

The SDK's `BearerAuthBackend` will call `Auth0JWTVerifier.verify_token()`. For static bearer tokens (Phase 14), we need a second path. Two options:

**Option A (recommended): Composite TokenVerifier**
```python
class DualTokenVerifier:
    """Try Auth0 JWT first; fall back to SqliteKeyStore static tokens."""
    def __init__(self, jwt_verifier: Auth0JWTVerifier, store: SqliteKeyStore): ...
    async def verify_token(self, token: str) -> AccessToken | None:
        result = await jwt_verifier.verify_token(token)
        if result:
            return result
        # Fall back to static bearer token
        key_name = store.verify_token(token)
        if key_name:
            return AccessToken(token=token, client_id=key_name, scopes=[])
        return None
```

**Option B:** Keep `BearerAuthMiddleware` as a Starlette middleware on the outer app and remove it from the SDK path — but this creates two separate 401 response formats and may double-process requests.

Option A is cleaner and keeps D-08 logic in one place.

### Pattern 4: /.well-known/oauth-authorization-server Proxy Endpoint (CRITICAL)

**Verified bug (Claude.ai issue #82):** Claude.ai (web) ignores the `authorization_servers` field in the protected resource metadata and instead directly hits `MCP_SERVER/.well-known/oauth-authorization-server` and `MCP_SERVER/authorize`, `MCP_SERVER/token`. The mcp SDK's `create_protected_resource_routes` serves `/.well-known/oauth-protected-resource/mcp` (RFC 9728), which is correct, but the Authorization Server metadata at `/.well-known/oauth-authorization-server` points to Auth0 — Claude must be able to reach Auth0's discovery doc via a proxy or be smart enough to follow the `authorization_servers` hint.

**Required additional routes on the MCP server** (for Claude clients that hit the root domain):
```python
# Proxy /.well-known/oauth-authorization-server to Auth0's own discovery doc
@mcp.custom_route("/.well-known/oauth-authorization-server", methods=["GET"])
async def auth_server_metadata(request: Request) -> JSONResponse:
    import httpx
    async with httpx.AsyncClient() as client:
        r = await client.get(f"https://{AUTH0_DOMAIN}/.well-known/oauth-authorization-server")
        return JSONResponse(r.json())
```

Auth0's discovery doc exposes its own `/authorize` and `/token` endpoints — clients that follow spec (RFC 9728 + RFC 8414) will redirect to Auth0 directly. Clients that follow old spec will try `MCP_SERVER/authorize` — which won't work without additional proxy routes.

**Decision point for planner:** The ROADMAP says success criterion #2 includes "a token endpoint and redirect-based auth flow." This conflicts with D-01 (no custom token endpoint). Recommend: serve the `/.well-known/oauth-authorization-server` proxy and document that Claude Code CLI is the primary test client (it follows current spec correctly).

### Anti-Patterns to Avoid

- **Passing `auth=` to FastMCP AND calling `app.add_middleware(BearerAuthMiddleware)`**: The SDK's auth routes and middleware are already in `streamable_http_app()` — adding `BearerAuthMiddleware` on top creates duplicate auth processing.
- **Setting `resource_server_url` to the root URL** instead of the `/mcp` path: The SDK constructs `/.well-known/oauth-protected-resource/mcp` — if you use the root, the path will be `/.well-known/oauth-protected-resource/` which is technically valid but less discoverable.
- **Caching nothing in PyJWKClient**: Fetching JWKS on every request adds 100–300ms latency per request. Set `cache_jwk_set=True, lifespan=300`.
- **Hardcoding trailing slash on Auth0 issuer**: Auth0 JWTs include trailing slash in `iss` claim (e.g., `https://tenant.auth0.com/`). PyJWT's issuer check is exact-match — must match exactly.

| Problem | Don't Build | Use Instead | Why |

## Common Pitfalls

### Pitfall 1: `issuer_url` Trailing Slash
**What goes wrong:** PyJWT's `decode()` fails with `InvalidIssuerError` even though the token is valid.
**Why it happens:** Auth0 tokens have `iss = "https://tenant.auth0.com/"` (trailing slash). If `issuer` passed to `jwt.decode()` is `"https://tenant.auth0.com"` (no slash), exact-match fails.
**How to avoid:** Always set `issuer = f"https://{AUTH0_DOMAIN}/"` with trailing slash.
**Warning signs:** `jwt.exceptions.InvalidIssuerError` in logs.

### Pitfall 2: Claude.ai Ignoring `authorization_servers` Field (Old Spec)
**What goes wrong:** Claude.ai hits `MCP_SERVER/.well-known/oauth-authorization-server`, `MCP_SERVER/authorize`, `MCP_SERVER/token` — none of which exist on a pure Resource Server.
**Why it happens:** Claude.ai web (as of late 2025) implements the March 2025 MCP auth spec, which required the MCP server to act as both AS and RS. The June 2025 spec added RS-only mode.
**How to avoid:** Serve `/.well-known/oauth-authorization-server` as a proxy to Auth0's discovery doc. Use Claude Code CLI for primary testing (it implements current spec).
**Warning signs:** `about:blank` in browser, no requests in MCP server logs from Claude.

### Pitfall 3: Cloudflare Bot Blocking
**What goes wrong:** Claude connector requests are blocked by Cloudflare before reaching the MCP server. Server logs show no requests from Claude.
**Why it happens:** Cloudflare's bot management flags Claude's user-agent as an AI bot scraper. Specifically, "Block AI Bots" setting treats Claude traffic the same as scraper bots.
**How to avoid:** In Cloudflare dashboard under Security → Bots, disable "Block AI Bots" or create a WAF bypass rule for the MCP domain and `/mcp` path for the Claude user-agent pattern (`claude*`).
**Warning signs:** Server receives zero requests from Claude; works fine from MCP Inspector or curl.

### Pitfall 4: Double Auth Processing
**What goes wrong:** Requests get 401 even with valid tokens because two middleware layers conflict.
**Why it happens:** `app.add_middleware(BearerAuthMiddleware)` runs on the outer Starlette app AND the SDK's `AuthenticationMiddleware` (wired by `streamable_http_app()` when `auth=` is set) both inspect the same `Authorization` header.
**How to avoid:** Use the composite `DualTokenVerifier` pattern (D-08 Option A). Remove standalone `BearerAuthMiddleware` from `server.py`; let the SDK's auth middleware handle both token types via `DualTokenVerifier`.
**Warning signs:** Valid static bearer tokens rejected after adding OAuth; logs show double "verify" calls.

### Pitfall 5: Auth0 Dynamic Client Registration Not Enabled
**What goes wrong:** Claude's DCR request (POST /register → Auth0) returns 404 or 403.
**Why it happens:** Auth0 does not enable OIDC Dynamic Client Registration by default. It requires a tenant setting change AND application-level configuration.
**How to avoid:** In Auth0 tenant: Settings → Advanced → enable OIDC Dynamic Client Registration. Also: promote social connections to domain-level so third-party clients (Claude DCR-registered) can use them.
**Warning signs:** `POST /register` returns error; Claude shows "does not support dynamic client registration."

### Pitfall 6: PUBLIC_PATHS Missing `/.well-known` Routes
**What goes wrong:** The `/.well-known/oauth-protected-resource/mcp` discovery endpoint returns 401.
**Why it happens:** The current `BearerAuthMiddleware` only allowlists `/health`. If it runs alongside SDK auth, it will block unauthenticated discovery requests.
**How to avoid:** Remove `BearerAuthMiddleware` from outer app and use `DualTokenVerifier` instead. The SDK's `RequireAuthMiddleware` correctly excludes well-known routes from auth enforcement.
**Warning signs:** OAuth client cannot discover resource metadata; requests to `/.well-known/*` return 401.
