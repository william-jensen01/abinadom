# Phase 16.1: OAuth 2.0 for Claude Desktop - Context

**Gathered:** 2026-04-06
**Status:** Ready for planning

<domain>
## Phase Boundary

Add OAuth 2.1 authentication so Claude Desktop (and future MCP clients) can connect via their built-in OAuth handshake — no manual bearer token copy-paste required. The server acts as a Resource Server only; Auth0 is the Authorization Server.

**What this phase delivers:**
- Auth0 tenant + application configuration (operator setup steps)
- `mcpauth` Python library integrated into the FastMCP/Starlette server
- `/.well-known/oauth-protected-resource` metadata endpoint (served automatically by mcp-auth)
- Claude Desktop completes its OAuth flow end-to-end: browser login → token → MCP requests work
- Existing bearer token auth remains functional for non-Claude Desktop clients

**What this phase does NOT deliver:**
- A custom Authorization Server (offloaded to Auth0 entirely)
- User management UI or admin dashboard
- Rate limiting or per-user scopes (future)
- Changes to the pipeline, ChromaDB, or MCP tools

</domain>

<decisions>
## Implementation Decisions

### Authorization Server

- **D-01:** Auth0 is the Authorization Server — handles user login, token issuance, and all OAuth spec compliance. No custom `/authorize` or `/token` endpoints needed on the MCP server.
- **D-02:** The MCP server is a pure Resource Server — it validates incoming tokens issued by Auth0. mcp-auth handles this validation and the protected resource metadata endpoint.
- **D-03:** Rationale: low maintenance. Auth0 updates as the MCP spec evolves; mcp-auth updates alongside it. No bespoke OAuth code to maintain.

### Identity Providers (Auth0)

- **D-04:** Enable Google and GitHub as social login providers in the Auth0 tenant. These cover the target user base (developer-focused LDS scripture tool). Additional providers can be added in Auth0 dashboard without touching server code.
- **D-05:** Auth0 Universal Login (hosted login page) handles the consent UI. The operator does not build a custom login page.

### MCP-Auth Library

- **D-06:** Use `mcpauth` Python library (pip package, MIT license, actively maintained by mcp-auth org). It handles:
  - Serving `/.well-known/oauth-protected-resource` metadata (RFC 9728) automatically
  - Bearer token validation against Auth0's JWKS endpoint
  - Proper `WWW-Authenticate` headers on 401 responses
  - Injecting `authInfo` into request context
- **D-07:** `mcpauth` replaces or wraps the existing `BearerAuthMiddleware` for OAuth-authenticated requests. The integration point is the same: Starlette ASGI middleware layer.

### Coexistence with Existing Bearer Tokens

- **D-08:** Existing bearer token auth (Phase 14 `SqliteKeyStore`) must remain functional for non-Claude Desktop clients (roadmap success criteria #3). The middleware stack must support both:
  - OAuth tokens validated via mcp-auth (Auth0 JWT validation)
  - Static bearer tokens validated via `SqliteKeyStore` (SHA-256 hash lookup)
  - How to layer these is Claude's discretion — could be a dual-path middleware or mcp-auth configured to accept both.

### Auth0 Configuration

- **D-09:** Auth0 tenant settings needed (operator setup, not code):
  - Create Auth0 tenant
  - Create a "Regular Web Application" or "Machine to Machine" application for the MCP server
  - Enable Google and GitHub social connections
  - Add Claude Desktop's callback URL (`https://claude.ai/api/mcp/auth_callback`) to allowed redirect URIs
  - Configure PKCE (S256) — required by Claude Desktop
- **D-10:** Auth0 credentials (`AUTH0_DOMAIN`, `AUTH0_AUDIENCE`) added to `.env` and `.env.example`.

### Token Lifetime

- **D-11:** Defer to Auth0 defaults for token lifetime. Auth0 issues short-lived access tokens with refresh token support by default. Operator can adjust in Auth0 dashboard without code changes. No custom token lifetime logic in the server.

### Claude's Discretion

- Exact `mcpauth` integration pattern (middleware order, config structure)
- Whether existing `BearerAuthMiddleware` is refactored to sit alongside mcp-auth or replaced by it
- Auth0 audience value (typically the MCP server's base URL, e.g. `https://mcp.yourdomain.com`)
- Whether `AUTH0_DOMAIN` and `AUTH0_AUDIENCE` are loaded at server startup (lifespan) or at module level
- `mcpauth` version to pin in Pipfile

</decisions>

<specifics>
## Specific Ideas

- The driving motivation for OAuth is sharing: this server will eventually be shared with other users who should not need to manually generate and paste bearer tokens. Auth0 + Google/GitHub login is the user-facing experience that makes onboarding frictionless.
- Auth0 was chosen specifically for its low maintenance profile: updates to OAuth spec compliance, token handling, and social provider integrations are handled by Auth0 and mcp-auth — the operator doesn't need to track spec changes.
- The deployment target is a home server (Dell PowerEdge R720) behind Cloudflare Tunnel — HTTPS is already guaranteed by Caddy + Cloudflare (Phase 16). All Auth0 callback URLs will be HTTPS.

</specifics>

<deferred>
## Deferred Ideas

- **Per-user scopes / RBAC** — Auth0 supports role-based access control. Useful if some users get read-only access and others get more. Not needed now (all users get the same tools).
- **Usage logging per OAuth user** — Current usage log (Phase 14) logs by key name. OAuth users would log by Auth0 user ID. Can be added once mcp-auth is wired and `authInfo` is available in the middleware.
- **Cloudflare Access** — Could add a second auth layer at the Cloudflare Tunnel level. Future consideration if abuse is observed.
- **Rate limiting** — AUTH-05 in REQUIREMENTS.md. Defer until user base grows.
- **Auth0 Management API integration** — Operator could issue/revoke user access via Auth0 dashboard instead of `manage_keys.py`. No code needed; just operator workflow.

</deferred>
