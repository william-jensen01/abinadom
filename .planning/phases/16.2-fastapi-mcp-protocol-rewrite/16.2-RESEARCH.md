## Summary

Phase 16.2 replaces the entire FastMCP + BaseHTTPMiddleware stack with a FastAPI app that manually dispatches MCP JSON-RPC over HTTP POST. The root cause of the rewrite is structural: FastMCP uses anyio task groups internally, and `BaseHTTPMiddleware.call_next()` runs downstream handlers in a new async scope that severs the task group context, producing `RuntimeError: Task group is not initialized`. This is unfixable without replacing FastMCP.

The replacement is straightforward: a single FastAPI `POST /` route reads the JSON-RPC body, dispatches on `method`, and applies per-method auth logic inline — no middleware wrapping is needed. Tool logic (`search`, `get_talk`) is unchanged; it is called directly from the dispatcher using the same `AppContext` pattern. Session management is a simple in-memory UUID dict.

FastAPI is not currently installed in the project environment. It must be added to Pipfile and requirements.txt as part of this phase. Starlette 1.0.0 is already installed (FastAPI depends on Starlette), so the version constraint is forward-compatible. The `TestClient` from `starlette.testclient` (already used in `test_server.py`) works with FastAPI apps with no changes to the test harness.

**Primary recommendation:** Use `fastapi.FastAPI` + `@app.post("/")` for the MCP dispatcher, `fastapi.testclient.TestClient` (or `starlette.testclient.TestClient`) for tests, and `uuid.uuid4()` for session IDs. No new testing libraries are needed.

### Pattern 1: FastAPI Lifespan with AppContext

FastAPI 0.95+ supports a `lifespan` async context manager replacing the old `@app.on_event("startup")` pattern. This is the correct way to run startup validation and share `AppContext` with route handlers.

```python
# Source: FastAPI docs — https://fastapi.tiangolo.com/advanced/events/
from contextlib import asynccontextmanager
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    # Startup — runs once before first request
    ctx = _startup()          # raises SystemExit(1) on failure
    app.state.ctx = ctx       # store on app.state for route access
    yield
    # Shutdown (no-op for ChromaDB PersistentClient)

app = FastAPI(lifespan=lifespan)
```

**Key difference from FastMCP:** `AppContext` is stored on `app.state` (accessed via `request.app.state.ctx`), not via FastMCP's `ctx.request_context.lifespan_context`. This changes how tool functions access the context — they receive `Request` as a parameter and read `request.app.state.ctx`.

[CITED: https://fastapi.tiangolo.com/advanced/events/]

### Pattern 2: MCP JSON-RPC Dispatcher (single POST endpoint)

The MCP Streamable HTTP transport uses a **single POST endpoint** for all JSON-RPC messages. The dispatcher reads `method` from the body and routes to the appropriate handler. Auth is applied per-method inside the dispatcher — not in middleware.

```python
# Source: MCP spec — https://modelcontextprotocol.io/specification/draft/basic/transports
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

@app.post("/")
async def mcp_dispatcher(request: Request) -> JSONResponse:
    body = await request.json()
    method = body.get("method")
    req_id = body.get("id")           # None for notifications

    if method == "initialize":
        return await _handle_initialize(body, request)

    # All other methods require a valid session
    session_id = request.headers.get("mcp-session-id")
    if not session_id or session_id not in _sessions:
        return _error_response(req_id, -32600, "Invalid session", 400)

    if method == "notifications/initialized":
        return JSONResponse({}, status_code=202)   # session already recorded

    # tools/list and tools/call require OAuth token
    token_payload = _verify_auth(request)
    if token_payload is None:
        return _unauthorized_response()

    if method == "tools/list":
        return await _handle_tools_list(body, request)
    elif method == "tools/call":
        return await _handle_tools_call(body, request)
    else:
        return _error_response(req_id, -32601, f"Method not found: {method}", 404)
```

[CITED: https://modelcontextprotocol.io/specification/draft/basic/transports]

### Pattern 6: tools/call — Bridging to Existing Tool Functions

The existing `search()` and `get_talk()` functions use `ctx.request_context.lifespan_context` to get `AppContext`. After the rewrite, they receive `AppContext` directly from `request.app.state.ctx`. Two approaches:

**Option A (preferred): Pass AppContext directly — refactor tool signatures.**
Remove the FastMCP `Context` parameter; pass `AppContext` directly. Test functions use `asyncio.run()` as they do today.

**Option B: Build a mock `ctx` object — zero changes to tool signatures.**
Construct a mock `ctx` matching the FastMCP interface, populated from `request.app.state.ctx`. Zero changes to `search()` / `get_talk()` or their tests.

Option B has lower risk (zero changes to tested code), but Option A is cleaner. CONTEXT.md says tool logic is kept — Option B keeps it most faithfully.

```python
# Option B: minimal-change bridge in tools/call handler
class _FakeMCPCtx:
    class _Inner:
        def __init__(self, ctx):
            self.lifespan_context = ctx
    def __init__(self, app_ctx):
        self.request_context = self._Inner(app_ctx)

async def _handle_tools_call(body: dict, request: Request) -> JSONResponse:
    params = body.get("params", {})
    tool_name = params.get("name")
    arguments = params.get("arguments", {})
    app_ctx = request.app.state.ctx
    fake_ctx = _FakeMCPCtx(app_ctx)

    if tool_name == "search":
        result_text = await search(**arguments, ctx=fake_ctx)
    elif tool_name == "get_talk":
        result_text = await get_talk(**arguments, ctx=fake_ctx)
    else:
        return _error_response(body.get("id"), -32602, f"Unknown tool: {tool_name}", 404)

    return JSONResponse({
        "jsonrpc": "2.0",
        "id": body.get("id"),
        "result": {
            "content": [{"type": "text", "text": result_text}],
            "isError": False,
        },
    })
```

[CITED: https://modelcontextprotocol.io/specification/2025-11-25/server/tools — CallToolResult format]

### Pattern 7: Auth Verification Inside Dispatcher

```python
def _verify_auth(request: Request) -> dict | None:
    """Check Authorization header and return payload or None."""
    auth_header = request.headers.get("authorization", "")
    if not auth_header.startswith("Bearer "):
        return None

    token = auth_header[len("Bearer "):]

    if _jwt_verifier is not None:
        return _jwt_verifier.verify_token(token)
    else:
        # Static fallback: SqliteKeyStore
        key_name = _key_store.verify_token(token)
        return {"sub": key_name} if key_name else None
```

### Anti-Patterns to Avoid

- **Global session state across processes:** In-memory `_sessions` dict is lost on restart. This is acceptable (MCP clients re-initialize). Never use a file-based session store without locking.
- **Reading request body twice:** FastAPI caches the body via `await request.json()` — safe to call once. Do not call `await request.body()` after `await request.json()`.
- **Applying middleware for per-method auth:** Middleware cannot inspect the method field without reading the body, making it unreliable. Auth belongs inside the dispatcher.
- **Returning `application/json` with SSE content:** This phase uses plain `application/json` responses only. Do not implement SSE streaming (deferred).
- **Forgetting `MCP-Protocol-Version` header in all responses:** The spec requires this header on every response from `initialize` onward. Set it in a response helper.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| JSON Schema for tool inputs | Custom dict | Standard JSON Schema dict literal | MCP spec defines the format; just write the dict correctly |
| Session ID generation | Sequential int | `uuid.uuid4()` | UUIDs are cryptographically unique; spec requires globally unique session IDs |
| JWT parsing | Manual base64 decode | `jwt.get_unverified_header()` (PyJWT) | Already in use; handles malformed tokens safely |
| HTTP test client | `requests` or `httpx` directly | `starlette.testclient.TestClient` | Already used; runs sync; no event loop management needed |
| Auth0 userinfo HTTP call | `urllib` | `httpx.Client` (sync) | Already used in `auth/oauth.py`; handles timeouts |

**Key insight:** The MCP JSON-RPC dispatcher is genuinely simple — 4 methods, no batching, no streaming in this phase. Resist the temptation to reach for a JSON-RPC framework. A plain dict dispatch (`method_handlers = {"initialize": ..., "tools/list": ..., ...}`) is more readable and easier to test than any library abstraction.

## MCP Protocol Facts (Verified)

### initialize Request/Response

**Request from client:**
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-03-26",
    "capabilities": {"roots": {"listChanged": true}, "sampling": {}},
    "clientInfo": {"name": "Claude Desktop", "version": "1.0.0"}
  }
}
```

**Server response:**
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2025-06-18",
    "capabilities": {"tools": {}},
    "serverInfo": {"name": "lds-scripture-index", "version": "1.0.0"},
    "instructions": "..."
  }
}
```

**Why `initialize` must be unauthenticated:** The OAuth flow cannot begin until the client knows which Authorization Server to use. The client discovers this from `/.well-known/oauth-protected-resource`, which it finds from the `WWW-Authenticate` header on a 401 response from `tools/list`. But to trigger that 401, the client must first complete `initialize` and `notifications/initialized`. If `initialize` required a token, the client would have no way to bootstrap the OAuth flow. [CITED: https://modelcontextprotocol.io/specification/2025-03-26/basic/lifecycle]

### notifications/initialized

```json
{"jsonrpc": "2.0", "method": "notifications/initialized"}
```

This is a notification (no `id` field). Server responds `202 Accepted` with empty body. [CITED: https://modelcontextprotocol.io/specification/2025-03-26/basic/lifecycle]

### Session ID Header

The spec uses `MCP-Session-Id` (capital I, lowercase d). Client MUST include it on all subsequent requests after `initialize`. Server SHOULD return 400 if session ID is missing on non-initialize requests. Server returns 404 if session ID is unknown (forces re-initialize). [CITED: https://modelcontextprotocol.io/specification/draft/basic/transports]

### MCP-Protocol-Version Header

Client MUST send `MCP-Protocol-Version: <negotiated-version>` on all subsequent requests. If server receives an unsupported version, it MUST return 400 Bad Request. [CITED: https://modelcontextprotocol.io/specification/draft/basic/transports]

### GET / vs HEAD /

The spec says the MCP endpoint supports GET (for SSE subscription). For this phase: return `405 Method Not Allowed` with `Allow: POST, HEAD, DELETE`. HEAD returns 200 with `MCP-Protocol-Version` header per CONTEXT.md connection flow.

### DELETE / (Session Cleanup)

Client SHOULD send `DELETE /` with `MCP-Session-Id` when done. Server removes session from dict, returns 200. Server MAY return 405 if it doesn't support client-initiated termination — but implementing it is simple and correct. [CITED: https://modelcontextprotocol.io/specification/draft/basic/transports]

## Common Pitfalls

### Pitfall 1: FastAPI Not Installed
**What goes wrong:** `ImportError: No module named 'fastapi'` at server startup or test time.
**Why it happens:** FastAPI is not in Pipfile — it was never needed while FastMCP was used.
**How to avoid:** Add to Pipfile (`pipenv install fastapi`) and update `requirements.txt` for Docker (`pipenv run pip freeze | grep fastapi`).
**Warning signs:** Import error in first test run after rewrite.

### Pitfall 2: `app.state.ctx` Not Set When Tests Run
**What goes wrong:** Tests that call the dispatcher get `AttributeError: 'State' object has no attribute 'ctx'` because FastAPI lifespan is not triggered by `TestClient` in certain configurations.
**Why it happens:** `TestClient` does run the lifespan by default when used as a context manager (`with TestClient(app) as client:`), but not when instantiated directly without `with`.
**How to avoid:** Always use `TestClient` as a context manager in tests that invoke the dispatcher; OR mock `app.state.ctx` directly in the test setup.
**Warning signs:** `AttributeError` on `request.app.state.ctx` in dispatcher tests.

### Pitfall 3: Body Double-Read Breaks JSON Parsing
**What goes wrong:** Body is empty when the dispatcher calls `await request.json()` because something else already consumed the stream.
**Why it happens:** FastAPI/Starlette body reads are streaming; calling `await request.body()` before `await request.json()` leaves the stream empty.
**How to avoid:** Call `await request.json()` once at the top of the dispatcher, store the result in `body`.
**Warning signs:** `json.JSONDecodeError` on a valid POST body.

### Pitfall 4: Session ID Header Case Sensitivity
**What goes wrong:** MCP clients send `MCP-Session-Id` but dispatcher looks for `mcp-session-id` (or vice versa).
**Why it happens:** HTTP header names are case-insensitive in the spec, but Python dict lookups are case-sensitive. FastAPI/Starlette normalizes header names to lowercase in `request.headers`.
**How to avoid:** Always use lowercase when reading from `request.headers`: `request.headers.get("mcp-session-id")`.
**Warning signs:** Session check fails even though client sent the header.

### Pitfall 5: test_server.py Tests That Reference FastMCP
**What goes wrong:** Multiple existing `test_server.py` tests will fail after the rewrite:
- `test_mcp_has_instructions` — tests `mcp.instructions` (FastMCP attribute, removed)
- `test_mcp_host_port_defaults` — tests `mcp.settings.host/port` (FastMCP attribute, removed)
- `test_entry_point_transport` — greps source for `streamable_http_app()` and `add_middleware(BearerAuthMiddleware` (both removed)
- `test_no_stdio_references` — this one is safe and can be kept/updated

**Why it happens:** These tests were written to verify Phase 14 decisions. Phase 16.2 supersedes them.
**How to avoid:** Rewrite `test_server.py` as part of the plan — replace removed tests with dispatcher behavior tests.
**Warning signs:** 5+ immediate failures in `test_server.py` on first run after rewrite.

### Pitfall 6: 401 Response Missing `WWW-Authenticate` Header
**What goes wrong:** MCP clients (Claude Desktop, Cursor) cannot discover the Auth0 Authorization Server because the 401 response lacks the `WWW-Authenticate: Bearer resource_metadata="..."` header.
**Why it happens:** Standard HTTP 401 responses omit this header; it must be set explicitly per RFC 9728.
**How to avoid:** In `_unauthorized_response()`, always include `WWW-Authenticate: Bearer resource_metadata="{MCP_BASE_URL}/.well-known/oauth-protected-resource"` when `MCP_BASE_URL` is set.
**Warning signs:** Claude Desktop OAuth flow stalls at "connecting" without any error.

### Pitfall 7: `_FakeMCPCtx` Breaking Tool Tests
**What goes wrong:** If Option B (fake ctx bridge) is used, changes to the `_FakeMCPCtx` struct could silently break `search()` and `get_talk()`.
**Why it happens:** Tool functions access `ctx.request_context.lifespan_context` — this is a nested attribute chain that must match exactly.
**How to avoid:** The existing tool tests in `test_server.py` (`TestSearchTool`, `TestGetTalkTool`) already use a `_make_mock_ctx()` helper that builds the same structure — verify both use identical patterns.
**Warning signs:** Tool tests pass but live calls fail with `AttributeError`.

def verify_token(self, token: str) -> dict | None:
    try:
        header = jwt.get_unverified_header(token)

## Open Questions

1. **Option A vs Option B for tool function signatures**
   - What we know: Both approaches work; Option A (refactor signatures) is cleaner; Option B (fake ctx) has zero risk to existing tool tests.
   - What's unclear: Whether CONTEXT.md's "all tool logic unchanged" means signatures too, or just behavior.
   - Recommendation: Use Option B (fake ctx) to be maximally conservative; tool function signatures are unchanged, tests are unchanged.

2. **Whether GET / should return 405 or 200 with SSE headers**
   - What we know: MCP spec says server MUST support GET for SSE subscription or return 405.
   - What's unclear: Claude Desktop and Cursor behavior when receiving 405 on GET /.
   - Recommendation: Return 405 with `Allow: POST, HEAD, DELETE` per spec. Clients will not rely on SSE if 405 is returned cleanly.

3. **Logging for authenticated requests (AUTH-03)**
   - What we know: `BearerAuthMiddleware._extract_tool_name()` currently handles usage logging.
   - What's unclear: Whether to replicate this log inside the dispatcher or create a helper.
   - Recommendation: Move logging into `_handle_tools_call()` and `_handle_tools_list()` directly; keep the same `SqliteKeyStore.log_request()` call.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | Yes | `JWKSVerifier.verify_token()` — RS256 via JWKS, HS256 via /userinfo |
| V3 Session Management | Yes | UUID session IDs (cryptographically unique); in-memory dict; session required for all post-initialize requests |
| V4 Access Control | Yes | Per-method auth inside dispatcher; `initialize` always public; `tools/*` always protected |
| V5 Input Validation | Yes | `method` field from JSON body; tool arguments passed through to existing validated functions |
| V6 Cryptography | Partial | JWT verification uses PyJWT (standard library) — never hand-rolled |

### Known Threat Patterns for this Stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Session fixation | Tampering | Server generates UUID session ID; client cannot choose its own |
| Token replay after expiry | Tampering | PyJWT validates `exp` claim; `/userinfo` validates server-side |
| DNS rebinding | Spoofing | MCP spec says validate `Origin` header — CONTEXT.md does not mention this; flag as open question |
| Missing `WWW-Authenticate` header | Elevation of privilege | OAuth discovery breaks; always include header on 401 |
| Passing tool arguments without validation | Tampering | Existing `search()` / `get_talk()` helpers already sanitize inputs — no regression risk |

**DNS rebinding note:** The MCP transport spec explicitly requires `Origin` header validation on all incoming connections to prevent DNS rebinding attacks. The CONTEXT.md does not mention this. The planner should include `Origin` header validation in the POST handler, or document why it is deferred (e.g., running behind Cloudflare Tunnel which provides this protection). [CITED: https://modelcontextprotocol.io/specification/draft/basic/transports — Security Warning section]
