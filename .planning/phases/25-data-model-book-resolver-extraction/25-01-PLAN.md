Add `clean_verse_text` — the single decode-and-clean entry point that scripture extraction will
use for every verse — to the shared HTML utility module, with synthetic unit coverage.

Purpose: EXT-03 requires verse `Text` to arrive UTF-8-decoded, entity-decoded, and free of
residual HTML tags. `scripture.Text` cells come back from sqlite3 as `bytes`, and 20 real verses
(all of D&C 77) carry line-break markup. This function is the whole mitigation, and it is the
only edit this phase makes to a module the talk pipeline already depends on.

`tests/test_html_parsing_utils.py`.

  <behavior>
    - `bytes` input is decoded as UTF-8 and returns a `str`
    - `str` input is accepted unchanged as input type and returns a `str`
    - Plain text with no markup and no entities passes through with surrounding whitespace stripped
    - `&amp;` decodes to an ampersand
    - `&nbsp;` becomes a regular space, never a non-breaking space character
    - A verse whose only markup is a self-closing line break with no adjacent whitespace comes back
      with the two words separated by a single space, not concatenated
    - Markup-bearing input returns text with no less-than character remaining
    - Nested or malformed markup still returns tag-free text
    - Runs of whitespace (including newlines and tabs) collapse to a single space
    - Empty input and whitespace-only input return an empty string rather than raising or returning None
    - Valid non-ASCII text (curly quotes, em-dash) survives unchanged — it is not stripped or re-encoded
    - Invalid UTF-8 bytes raise rather than silently producing replacement characters
  </behavior>
  <action>
    Add `clean_verse_text(raw)` in a new banner section near `render_span_text`, matching the
    surrounding docstring style. Add the stdlib `html` import — it is the only new import.

    Decode first (D-03): `bytes` decode as strict UTF-8 so a future corrupt DB fails loudly instead
    of yielding replacement characters; the current corpus has zero decode failures across all
    73,267 S/J/F rows, so strictness costs nothing and buys a real alarm. Take a fast path when the
    decoded text contains no less-than character — `html.unescape` only (D-02; verified, only 20 of
    73,257 verses carry markup, so this is the ~99.97% case and BeautifulSoup overhead is pure
    waste). Fall back to `BeautifulSoup(..., "html.parser").get_text(separator=" ")` when markup is
    present: the separator argument is mandatory, because without it adjacent words on either side
    of a line-break tag are concatenated (Pitfall 3, reproduced against the real D&C 77 rows). Use
    `"html.parser"` explicitly to match the module's `CITATION_HTML_PARSER` convention and to avoid
    an lxml dependency.

    Both paths then converge on one normalization tail — replace the non-breaking space with a
    regular space, collapse whitespace runs, strip — because `html.unescape` turns `&nbsp;` into a
    non-breaking space rather than a space (Pitfall 2), and it would otherwise leak into stored text
    and embeddings. Reuse `render_span_text`'s existing idiom for this rather than inventing a
    second one, but collapse all whitespace (not only runs of literal spaces) so the tag fallback's
    injected separators and any newlines normalize too.
  </action>
