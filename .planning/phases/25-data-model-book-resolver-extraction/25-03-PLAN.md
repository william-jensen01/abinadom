  <action>
    Create `models/scripture_data.py` with the repo's `sys.path` header shim and a module docstring
    naming this as the Phase 25 scripture data model. Declare `VARIANT_BY_FLAG` as a module
    constant and derive the valid-variant set from its values rather than writing a second literal
    set — two hand-maintained lists of the same closed vocabulary is the drift this avoids.

    Declare `ScriptureVerse` with the SPEC section 4 fields: the scripture id, book id, canonical
    book name, book abbreviation, cite abbreviation, volume, chapter, verse, variant, source flag,
    reference, and text as required fields, then `context_window` defaulting to an empty string.
    `context_window` is deliberately unfilled here — Phase 26 computes it, and giving it a default
    keeps this phase's extractor from having to fabricate a value it has no basis to produce.

    exception hierarchy outside `db.SchemaError`). This validation is the last structural gate
    before verse data reaches the vector store in Phase 27, so it must reject rather than coerce:
    empty or whitespace-only text, a chapter or verse below 1, a non-positive scripture id, an
    empty book name, a variant outside the derived set, and a source flag outside the
    `VARIANT_BY_FLAG` keys. Name the scripture id in every message so a failure in a 73,000-row
    run is locatable.

    Add a `doc_id` property rendering the SPEC section 5 identity (the verse prefix joined to the
    scripture id). It is derived identity and the record owns it; leaving it to Phase 27 would put
    the format in the loader where the dedup key is not defined. Do NOT add a record-preparation
    method — the document/metadata/vector tuple shape belongs to Phase 27's loader, not here.

    The model validates; it never derives. Do NOT clean text, normalize a book name, map a flag to
    a variant, or build a reference inside this file — those are `clean_verse_text`'s,
    `book_resolver`'s and the extractor's jobs respectively, and duplicating them here would create
    a second normalization path (the exact anti-pattern this phase's responsibility map forbids).
    Import nothing beyond the stdlib: this module must import cleanly in the Phase 28 MCP server
    process with no database file present, which the import-hygiene test enforces by parsing this
    module's own source with `ast`.

  </read_first>
  <behavior>
    - `group_key` returns the book, chapter and variant of a verse as a triple
    - `BookVerses.key` returns the same triple as `group_key` applied to any of its members
    - A container built from consistent verses reports a count equal to its verse-list length
    - A container whose declared book, chapter or variant disagrees with any member raises `ValueError`
    - An empty verse list raises `ValueError`
    - Verses out of ascending verse-number order raise `ValueError`
    - A jst container holding two members with the same verse number but different source flags is
      accepted
    - A container with a verse-number gap is accepted — jst chapters are legitimately sparse
    - `to_dict` includes the key fields, the count, and the serialized members
  </behavior>
  <action>
    Add `group_key(verse)` as a module function and `BookVerses` as a dataclass carrying the book,
    chapter, variant and verse list. Define the key in exactly one place — `BookVerses.key`
    delegates to `group_key` — so the extractor's grouping and the container's self-description can
    never disagree.

    `__post_init__` enforces group coherence: non-empty, every member's key equal to the
    container's, and verse numbers non-decreasing. Do NOT enforce uniqueness of verse numbers
    within a group. Both J and F rows carry the jst variant, so a JST parallel verse and a JST
    fragment for the same reference legitimately land in the same container and are disambiguated
    by their source flag — a uniqueness assertion would fail on correct data. Do NOT warn or raise
    on verse-number gaps either: canonical chapters are contiguous but jst is sparse by nature
    (research measured 19% of J and 46% of F chapter groups as non-contiguous), and gap detection
    for canonical verses is Phase 26's validation job, not this container's.

    Expose a count derived from the verse list rather than a separately-passed total — the analog
    `TalkParagraphs` takes a total and checks it, but that pattern exists there because the talk
    extractor computes totals independently; here there is no second source to cross-check, so a
    stored total would be a field that can only ever be wrong.
  </action>
