<objective>
Build `config/book_resolver.py` — the single authority for what a scripture book is called.
`canonicalize()` turns the 99 raw `book` rows into canonical digit-form records once at build
time; `resolve()` maps any common user input form onto exactly those canonical names.

Purpose: EXT-04 and RES-01. This module is the shared dependency Phase 27 (pipeline) and Phase 28
(`get_verse` / `search`) both consume, and its canonical output must equal the `book` value the
extractor stores — a property this phase controls end to end.

Output: `config/book_resolver.py` and `tests/test_book_resolver.py`.
</objective>

      leaves the first entry intact and logs a warning
    - Across the full 94-book input the only alias key claimed by two different book rows resolves
      to the same canonical name
    - Every index value is a canonical name present in the canonicalize output

    normalization applied to both registration keys and caller input — one function, so a form that
    registers can never fail to look up.

    Declare the prefix set as a module-level `ALIAS_PREFIXES` ordered longest-first, covering the
    leading epistle and article forms the DB actually uses ("The Epistle to the ", "The Epistle of ",
    "To the ", "The Book of ", and a bare "The "). Strip in normalized space and register every
    distinct result *in addition to* the unstripped form — this is what makes RES-01's "any common
    input form" true, because the DB stores "The Epistle to the Romans" and users type "Romans"

    Iterate books in a stable id order so registration is deterministic, and on a conflicting key
    keep the first registration and log a warning rather than raising: research scanned the whole
    table and found exactly one collision, `d and c`, where both claimants canonicalize to the same
    name — benign and self-consistent — so raising would fail on correct data while a silent
    overwrite would make the outcome order-dependent.

    Register nothing for the five volume rows. `canonicalize` already excluded them, and the D&C
    volume needs no special handling because the Sections container's own CiteAbbr is already the
    D&C abbreviation and its canonical name is already "Doctrine and Covenants" — so both forms
    register naturally from the book record. The deliberate consequence is that a volume name alone
    resolves to nothing, which is correct: `resolve` answers "which book", and volume filtering is a
    separate Phase 28 parameter.

    Official Declarations, the Abraham facsimiles). State this in the module docstring as a named
    contract — `resolve` answers "which book is this name", never "does that book have retrievable
    verses" — because Phase 28's deferred error contract builds directly on it. Two reasons decide
    it this way. Filtering to the 87 verse-bearing books would need either a `scripture` query (this
    module reads the `book` table only) or a hardcoded seven-book exclusion list, which is brittle
    across DB version bumps for the same reason id-keyed hardcoding was rejected in CONTEXT. And a
    registered verse-less book lets Phase 28 answer "Official Declarations exists but v1 stores no
    verses for it" instead of "unknown book", which is strictly the more useful failure.
