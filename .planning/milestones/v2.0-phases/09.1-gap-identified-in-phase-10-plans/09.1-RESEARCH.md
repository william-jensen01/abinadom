## Summary

Phase 9.1 is a surgical, two-file change. The existing `prepare_paragraph_records()` function in `extractors/phase6_chromadb_loader.py` transforms `ParagraphData` objects into ChromaDB records but never received talk-level fields because `TalkMetadata` was not passed to it. The function currently sits at line 129 and its single call site is at line 278 inside `prepare_talk_bundle()`. At that call site, `metadata: TalkMetadata` is already in scope — it is used on the next line (281) to call `prepare_talk_record(metadata, annotation_texts)`. The fix is additive: add `talk_metadata=None` to the signature and inject the 4 scalar fields into `flat_meta` after `_flatten_metadata` runs.

The VER-06 check is equally well-bounded. All five existing VER checks in `scripts/verify_pipeline.py` follow an identical pattern: a `check_*()` function that opens collections, runs spot checks, prints status, and returns a dict with `passed` + details. VER-06 follows the same structure. It must cross-reference the paragraphs collection against the talks collection to confirm the 4 enriched fields are present and match.

The existing test suite (55 tests, 0 failures) covers `prepare_paragraph_records()` in `TestPrepareParagraphRecords` — six tests exist there. New tests must be added to cover the enrichment path (with `talk_metadata` provided) and the backward-compatible path (`talk_metadata=None`, current behavior).

**Primary recommendation:** Inject the 4 fields directly after `_flatten_metadata(raw_meta)` returns, as 4 explicit key assignments to `flat_meta`. No helper, no loop. VER-06 samples 10 records from `conference_talk_paragraphs`, fetches the corresponding talk from `conference_talks`, and asserts all 4 fields match. Include a count-check sub-step: count paragraphs where `speaker_name` is set vs total, with >= 95% threshold.

### Pattern 1: Additive Optional Parameter

**What:** Add `talk_metadata: TalkMetadata | None = None` to a pure transformation function. When `None`, behavior is identical to current. When provided, inject 4 scalar fields into the already-flattened metadata dict.

**When to use:** Any time a downstream consumer needs denormalized fields that exist upstream in the call stack — add to signature instead of fetching separately.

**Example (the exact change):**
```python
# Before (line 129 in extractors/phase6_chromadb_loader.py)
def prepare_paragraph_records(
    paragraphs: TalkParagraphs,
) -> tuple[list[tuple[str, dict[str, Any], str]], list[str]]:

# After
def prepare_paragraph_records(
    paragraphs: TalkParagraphs,
    talk_metadata: TalkMetadata | None = None,
) -> tuple[list[tuple[str, dict[str, Any], str]], list[str]]:
```

**Injection point** — after `flat_meta = _flatten_metadata(raw_meta)` on the per-paragraph loop, before `records.append(...)`:
```python
# Inject talk-level fields when metadata is provided (D-01, D-05)
if talk_metadata is not None:
    flat_meta["speaker_name"] = talk_metadata.speaker_name
    flat_meta["title"] = talk_metadata.title
    flat_meta["conference_year"] = talk_metadata.conference_year
    flat_meta["conference_month"] = talk_metadata.conference_month
```

Note: All 4 fields are simple scalars (str, str, int, str). They are already validated by `TalkMetadata.__post_init__`. No additional flattening needed — `_flatten_metadata` is not needed for these 4 fields because they are injected after it runs.

### Pattern 2: Caller Pass-Through (single call site)

**What:** The single call site at line 278 inside `prepare_talk_bundle()` already has `metadata` in scope. Update it to pass the parameter.

**Example (the exact change):**
```python
# Before (line 278)

# After
paragraph_records, annotation_texts = prepare_paragraph_records(
    paragraphs, talk_metadata=metadata
```

### Pattern 3: VER-0N check function structure

**What:** Every VER check in `verify_pipeline.py` is a standalone function `check_*(client, ef)` that returns a dict with `passed: bool` plus detail keys. The function itself prints its status. `main()` calls it, stores the result, includes it in the JSON report, and factors `passed` into the overall score.

The existing VER-05 (`check_topics`) is the closest analog for VER-06 — it does cross-collection verification: fetches IDs from SQLite as baseline, then cross-references ChromaDB. VER-06 differs: it fetches paragraph records from ChromaDB and cross-references the talks collection in ChromaDB (no SQLite needed).

**VER-06 structure:**
```python
def check_paragraph_enrichment(client: Any, ef: Any) -> Dict[str, Any]:
    """
    VER-06: Verify paragraph metadata enrichment.

    Spot-checks N paragraph records from conference_talk_paragraphs and
    asserts all 4 enriched fields (speaker_name, title, conference_year,
    conference_month) are present and match the corresponding talk record.
    Also checks coverage: >= 95% of paragraphs have speaker_name set.

    Returns:
        Dict with keys: passed, coverage_check, spot_check
    """
```

**VER-06 wiring in `main()`:**

### Pattern 4: VER-06 Cross-Collection Verification Logic

**Coverage sub-check:** Use `paras_col.get(limit=batch_size, include=["metadatas"])` paged in batches (matching VER-04 pattern) to count how many paragraph records have `speaker_name` set. Compare to `paras_col.count()`. Threshold: >= 95%.

**Spot-check sub-check:** Fetch a small sample (10 records) from paragraphs, extract `talk_id` from each, fetch the corresponding talk record from `conference_talks`, compare the 4 fields. All 4 must match exactly.

**Note on `_flatten_metadata` and type preservation:** `conference_year` is stored as `int` in `TalkMetadata` and is a scalar — `_flatten_metadata` preserves it as `int`. When read back from ChromaDB, it will be `int`. The comparison in VER-06 should use `==` without type coercion.

### Anti-Patterns to Avoid

- **Modifying `ParagraphData`:** The model is explicitly out of scope (D-03). Do not add `speaker_name` or other talk-level fields to the dataclass. Enrichment is a loading-layer concern.
- **Adding a migration script:** User preference is re-running Phase 6 via `run_pipeline.py --force`. No one-off migration scripts.
- **Injecting `session_description`:** Explicitly excluded per D-06, even though it is available on `TalkMetadata`.
- **Including the enrichment in `prepare_talk_bundle()` directly:** Keeping it in `prepare_paragraph_records()` means the transformation is self-contained and testable in isolation (consistent with existing unit test structure).
- **Overwriting existing paragraph fields:** The 4 injected fields are not present in `ParagraphData`, so there is no risk of collision. The 4 field names (`speaker_name`, `title`, `conference_year`, `conference_month`) do not appear anywhere in `ParagraphData` — confirmed by reading `models/paragraph_data.py`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Type conversion for 4 scalar fields | Custom type-checking logic | Direct assignment — all 4 are already validated scalars | `TalkMetadata.__post_init__` validates `speaker_name` (str), `title` (str), `conference_year` (int), `conference_month` (str) — no additional conversion needed |
| ChromaDB metadata flattening for injected fields | Additional `_flatten_metadata` call | Direct key assignment after `_flatten_metadata` returns | Fields are simple scalars, not lists or None — flattening is a no-op |
| VER-06 database baseline | SQLite join for expected values | Cross-reference talks collection in ChromaDB | The talks collection is the authoritative source for these 4 fields; avoids a third data source |

**Key insight:** The 4 fields are clean, validated scalars at injection time. No defensive coding needed for the injection itself — the complexity is entirely in the VER-06 verification logic.

## Common Pitfalls

### Pitfall 1: `talk_metadata` is None When Re-Running Tests

**What goes wrong:** Existing tests call `prepare_paragraph_records(paragraphs)` without `talk_metadata`. If the injection code is not gated on `if talk_metadata is not None`, a `NoneType` attribute error occurs.

**Why it happens:** The parameter is optional with default `None`. Tests that use the old call signature are not required to pass metadata.

**How to avoid:** Gate the entire injection block with `if talk_metadata is not None:`. This is the backward-compatibility guard specified in D-01.

**Warning signs:** `AttributeError: 'NoneType' object has no attribute 'speaker_name'` on existing test runs.

### Pitfall 2: Field Name Collision with Existing `ParagraphData` Fields

**What goes wrong:** Injecting a field that already exists in `flat_meta` from `asdict(para)` would silently overwrite it.

**Why it happens:** `flat_meta` is built from `asdict(para)` — all `ParagraphData` fields land there. If any of the 4 injected names collided, the injection would overwrite data.

**How to avoid:** Confirmed by reading `models/paragraph_data.py`: `ParagraphData` has no `speaker_name`, `title`, `conference_year`, or `conference_month` fields. Zero collision risk. No defensive check needed.

**Warning signs:** N/A — no collision, but if a future `ParagraphData` field is added with one of these names, the injection would silently overwrite it. The test suite would catch this.

### Pitfall 3: VER-06 Runs Before `--force` Re-Pipeline

**What goes wrong:** VER-06 is added and run immediately. The existing 202,175 paragraph records were loaded without the 4 fields. VER-06 fails the coverage check even though the code change is correct.

**Why it happens:** The ChromaDB database is persistent. The new code enriches records on write; old records are not updated until `run_pipeline.py --force` is run.

**How to avoid:** VER-06 should PASS only after `run_pipeline.py --force` completes. Document this clearly in the VER-06 function docstring and plan execution notes. The code change itself can be verified by the unit tests before the pipeline is re-run.

**Warning signs:** Coverage sub-check shows 0% paragraphs with `speaker_name` — this means the pipeline has not been re-run with the new code yet.

### Pitfall 4: VER-06 Coverage Check Performance

**What goes wrong:** Fetching all 202,175 paragraph metadata records to count `speaker_name` coverage is slow — potentially tens of seconds.

**Why it happens:** ChromaDB's `.get()` returns all metadata when `include=["metadatas"]`. 202,175 records is substantial.

**How to avoid:** Two options:
1. Use paged batching (matching VER-04's `batch_size=5000` pattern) — consistent with existing code.
2. Use a smaller spot-sample (e.g., 1000 records) instead of a full scan for the coverage check — faster, statistically sufficient.

Given that VER-04 already does a full scan of 202,175 paragraphs using the `batch_size=5000` pattern, the same approach is appropriate for VER-06 coverage check (consistency over optimization).

### Pitfall 5: `conference_year` Type Mismatch in VER-06

**What goes wrong:** `conference_year` stored in paragraph metadata as `int` is read back from ChromaDB as `int`, but the corresponding field in the talks collection may be stored differently.

**Why it happens:** `TalkMetadata.conference_year` is an `int`. `_flatten_metadata` preserves scalars as-is. Both should be `int` in ChromaDB. However, ChromaDB can sometimes return numeric metadata as `float` depending on the client version.

**How to avoid:** In VER-06, compare `int(para_meta.get("conference_year"))` vs `int(talk_meta.get("conference_year"))` to be defensive. This matches the existing pattern in VER-04 (`int(talk_id)` coercion).

```python
# Source: extractors/phase6_chromadb_loader.py:129
def prepare_paragraph_records(
    paragraphs: TalkParagraphs,
) -> tuple[list[tuple[str, dict[str, Any], str]], list[str]]:
    records: list[tuple[str, dict[str, Any], str]] = []
    annotation_texts: list[str] = []

    for para in paragraphs.paragraphs:
        if para.source_type == "annotation":
            annotation_texts.append(para.text)
            continue

        document = para.text
        raw_meta = asdict(para)
        flat_meta = _flatten_metadata(raw_meta)
        doc_id = f"para_{para.paragraph_id}"
        records.append((document, flat_meta, doc_id))

    return records, annotation_texts
```

## Open Questions

1. **VER-06 coverage check: full scan vs. sampled**
   - What we know: VER-04 does a full paginated scan of all 202,175 paragraphs using `batch_size=5000`. This takes a measurable but acceptable amount of time.
   - What's unclear: User preference for VER-06 — full scan (definitive) vs. sampled (faster). Per "Claude's Discretion" this is the researcher's recommendation to make.
   - Recommendation: Use a 1000-record sample for coverage check (randomly offset from start), and a 10-record spot-check for field-match verification. Keeps VER-06 fast. A 1000-record sample of 202,175 is statistically strong evidence.

2. **VER-06 run timing relative to `--force` pipeline**
   - What we know: VER-06 will fail until the pipeline is re-run. VER-06 code is correct; the database state is stale.
   - What's unclear: Should VER-06 detect and gracefully report "enrichment not yet applied" (warn) vs. hard-fail?
   - Recommendation: Hard-fail with a clear message. The verify script is only meaningful post-pipeline. A clear `FAIL` with `"0/1000 paragraphs have speaker_name set — run pipeline --force to enrich"` is unambiguous.
